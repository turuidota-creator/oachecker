# 采购付款关联单据展示与有限核对方案

## 背景
基于 OA 首页 `已办任务 -> 采购付款` 前 5 条真实样本的实际研究，采购付款单背后最稳定的关联链路不是单纯的“付款单 + 合同 + 验收”，而是：

`付款单 -> 国内PR -> 采购订单 -> 验收单 -> 合同约束`

但结合当前业务复杂度和字段稳定性，插件现阶段不适合做“全链路自动判定”。更合理的做法是：

- 国内 PR 只展示关键背景信息，不做自动判断
- 采购订单只做少量明确、稳定的硬规则判断
- 验收单只围绕邮件附件提供证据线索，不做强判定
- 合同沿用现有展示方式，仅作参考，不做自动判断

本方案的目标是把这条链做成插件里的正式能力，让财务在付款单页面就能看到关联单据、必要字段、有限自动核对结果，以及足够支持人工判断的上下文。

## 研究结论

### 1. 付款单的稳定入口是 `flowFormData`
付款单页面上看到的可点击关系，并不总是可靠的普通链接。真正稳定的结构来自：

- `cyouNeiOaServer/flowable/process/detail`
- 返回体里的 `flowFormData`

### 2. 付款单关联子表结构已经比较稳定

- `formtable_main_154_dt1`: 国内PR
- `formtable_main_154_dt2`: 采购申请单
- `formtable_main_154_dt3`: 采购价格反馈单
- `formtable_main_154_dt4`: 采购合同
- `formtable_main_154_dt5`: 采购订单
- `formtable_main_154_dt6`: 质量验收单

### 3. 前 5 条样本中的出现频率

- 国内PR：5/5
- 采购申请单：0/5
- 价格反馈单：5/5
- 合同：4/5
- 采购订单：4/5
- 验收单：5/5

### 4. link 字段不是总有
有流程号，不等于一定有可用的 link。

样本里实际情况：

- 国内PR link：4/5
- 价格反馈单 link：4/5
- 合同 link：4/5
- 采购订单 link：3/5
- 验收单 link：4/5

### 5. 关联信息不只在子表里
有些付款单的关联 PR / 验收号会出现在审批意见正文里，例如：

- `PR单号及相关流程：GNPR-...`
- `验收单：ZLYSD-...`

所以正式实现时，不能只扫子表，还要扫审批意见区。

## 方案调整原则

### 1. 付款单 vs 国内PR

- 国内 PR 仅展示，不做自动判断
- 重点展示 `归属部门`、`归属项目`、`用途说明`
- PR 金额仅作系统默认展示，不参与判断

### 2. 付款单 vs 采购订单

- 只保留两条自动核对规则：
  - 收款公司与订单供应商一致
  - 付款金额不超过订单金额
- 其他字段可以展示，但不参与自动判断

### 3. 付款单 vs 验收单

- 只需要查看验收单页面里的邮件附件
- 重点难点不是“能不能打开验收单页面”，而是“如何确认这封邮件说的就是这件付款对应的事情”
- 因此现阶段以证据展示和相关性线索为主，不做强自动结论

### 4. 付款单 vs 合同

- 沿用现有方案
- 仅展示，不判断

### 5. 全链路结论

- 现阶段不做“PR + 订单 + 验收 + 合同”的统一自动判定
- 自动判断范围收敛到采购订单的两条硬规则
- 其他链路统一为展示和人工判断辅助

## 财务经理视角的使用顺序

### 第一步：付款单
先确认本次付款的直接目标：

- 付款金额
- 收款公司
- 收款账号
- 发票是否取得

### 第二步：国内PR
把 PR 当作背景说明单据来看，只展示这些字段供人工判断：

- 费用归属部门
- 费用归属项目
- 费用用途说明
- PR 金额（系统默认展示，不参与判断）

### 第三步：采购订单
把采购订单当作本期唯一做硬判断的关联单据，只判断：

- 收款公司与订单供应商是否一致
- 付款金额是否不超过订单金额

### 第四步：验收单
把验收单当作交付证据页来看，重点关注：

- 页面中的邮件附件
- 邮件主题 / 邮件正文摘要
- 附件名称是否能说明交付内容
- 邮件内容是否明显指向本次付款对应事项

这里的核心不是自动得出“通过 / 不通过”，而是给财务足够的证据线索。

### 第五步：合同
合同继续作为参考约束层：

- 展示合同有效期
- 展示付款条件
- 展示税率、金额上限、账户信息
- 不做自动判断，由用户自行结合业务判断

## 产品目标
在付款单侧边栏新增一块 `关联单据核对`，按财务工作顺序展示：

1. 国内PR
2. 采购订单
3. 验收单
4. 合同

展示原则：

- 自动判断只覆盖最稳定的规则，不追求“全自动结论”
- 国内 PR 和合同以展示为主，不给通过 / 不通过
- 验收单以邮件附件和相关性线索为主，帮助人工判断
- 不要求用户自己打开多个子页面逐个查证
- 调试信息和原始证据放折叠区

## 核对规则建议

### A. 付款单 vs 国内PR

- 不做自动判断
- 仅展示 `归属部门`、`归属项目`、`用途说明`
- PR 金额只作为系统默认展示字段

### B. 付款单 vs 采购订单

- 收款公司与订单供应商一致
- 付款金额不超过订单金额

除了以上两条，不再追加其他自动核对规则。

### C. 付款单 vs 验收单

- 只抓取验收单页面中的邮件附件、邮件主题、邮件正文摘要
- 给出若干“是否相关”的提示线索，例如：
  - 邮件主题是否包含供应商名、项目名、订单名、交付关键词
  - 邮件正文是否包含与付款内容相关的关键词
  - 附件名是否包含验收报告、上线说明、交付清单等字样
- 不输出 `pass / fail` 结论
- 最终由用户人工判断这封邮件是否确实在说这件事

### D. 付款单 vs 合同

- 沿用现有字段展示方案
- 不输出自动判断结论

### E. 全链路

- 不做统一全链路自动结论
- 不做 PR、验收、合同之间的自动一致性判定
- 统一口径为：
  - PR：背景展示
  - 采购订单：有限自动核对
  - 验收单：邮件证据展示
  - 合同：约束参考展示

## 技术落地建议

### 1. 先从付款单 `flowFormData` 提关系
不要先靠 DOM 链接抓。

建议在 [detail.js](C:/Users/turui/Documents/OA_Payment_Audit_Rebuild_Project/oa_finance_audit_rebuild_extension/bg/detail.js) 新增或整理：

- `extractPaymentRelationRows(detail)`
- `normalizePaymentRelationRow(row, relationType)`

### 2. 国内PR走“展示提取”而不是“规则判断”
建议在 [analyzer.js](C:/Users/turui/Documents/OA_Payment_Audit_Rebuild_Project/oa_finance_audit_rebuild_extension/bg/analyzer.js) 中，将 PR 分析定位为：

- 抓到详情页
- 提取 `部门 / 项目 / 用途 / PR金额`
- 输出展示结构
- 不产生自动判断结论

### 3. 采购订单只保留两条硬规则
建议采购订单分析器只输出：

- `payeeMatchesSupplier`
- `paymentNotExceedOrderAmount`

避免继续扩展到内容语义一致性、项目一致性等不稳定规则。

### 4. 验收单聚焦邮件附件
建议验收单分析器重点做：

- 进入验收单页面
- 找到页面中的邮件主题、邮件正文、邮件附件
- 输出附件名列表和正文摘要
- 基于关键词做轻量 `relationHints`

不建议现阶段把验收单做成强规则引擎。

### 5. 合同沿用现有逻辑
合同部分继续沿用现有：

- 字段提取
- 条款展示
- 摘要展示

但在本方案中统一归类为“展示参考信息”，不参与自动判断。

### 6. 审批意见区继续作为补漏入口
当子表没有 link 时：

- 先从审批意见正文中提 `GNPR-` / `ZLYSD-` / `CYNCDD-` / `CYNCHT-`
- 再尝试补推 `detailUrl`

### 7. 接受“部分流程打不开”的现实
前端必须明确区分：

- 已找到 link 且可打开
- 已找到流程号但无 link
- 已找到 link 但权限不足
- 老 `workflow.cyou-inc.com` 域名不可达
- 页面是空壳页

## 分期实施建议

### Phase 1
先做：

- 国内PR展示
- 采购订单两条硬规则
- 合同沿用现有展示

输出：

- 页面展示
- 基础字段提取
- 采购订单自动核对结果

### Phase 2
增强：

- 验收单页面邮件主题 / 正文 / 附件提取
- 审批意见区补漏
- 老 history / old workflow 兼容

输出：

- 验收单邮件证据展示
- 相关性线索提示

### Phase 3
增强：

- 验收邮件相关性提示优化
- 更多异常场景提示
- 更清晰的“哪些是自动判断，哪些需要人工判断” UI 表达

说明：

- 即使到 Phase 3，也不建议轻易升级为“全链路自动结论”

## MVP 建议
如果只做最小可用版，建议优先级是：

1. 采购订单
2. 国内PR
3. 合同
4. 验收单

原因：

- 采购订单是当前唯一适合做稳定自动判断的链路
- 国内 PR 对财务理解背景很有帮助，但更适合展示
- 合同已有现成方案，可以直接沿用
- 验收单真正的难点在邮件内容相关性，需要放到后续渐进优化

## 结论
这次 5 条真实样本说明，采购付款场景下更合理的产品方向，不是“把所有关联单据都做成自动判定”，而是：

- 国内PR：展示背景
- 采购订单：做两条明确硬规则
- 验收单：展示邮件附件和相关线索
- 合同：沿用现有方案，仅作参考

因此下一步插件应新增一块 `关联单据核对`，但它的定位应该是：

`展示 + 有限自动核对 + 人工判断支撑`

而不是：

`全链路自动审批结论`
