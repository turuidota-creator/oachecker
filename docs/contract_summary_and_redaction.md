# 合同摘要与脱敏现状

这份文档只讲一件事：

- 当前合同付款摘要是怎么做的
- 发送给大模型的内容是什么
- 现在的脱敏强度到什么程度
- 这套方案为什么只适合内部 MVP，不适合作为最终保密方案

## 当前链路

当前合同摘要链路是：

1. 进入合同页
2. 下载合同附件
3. 读取 PDF / DOCX / 图片 OCR 文本
4. 本地筛付款相关候选条款
5. 对候选条款做脱敏
6. 发送给大模型生成结构化摘要
7. 本地还原 token，前端展示真实摘要

当前使用：

- endpoint: `https://api.siliconflow.cn/v1/chat/completions`
- model: `Qwen/Qwen2.5-32B-Instruct`

## 当前发给模型的不是整份合同

当前不会把整份合同全文直接发出去。

而是只发：

- `contract_context`
- `clause_candidates`

其中 `clause_candidates` 是本地筛出来的 top 候选段，默认上限 8 条。

## 当前本地怎么筛候选条款

主要在：

- [contract_terms.js](C:/Users/turui/Documents/Playground_oa_finance_rebuild/oa_finance_audit_rebuild_extension/bg/contract_terms.js)

当前筛选逻辑：

1. 先做文本清洗
2. 过滤明显的签章/联系人/地址/账户信息噪音行
3. 按标题和段落切 section
4. 在 section 里围绕这些关键词取句子窗口：
   - 付款
   - 支付
   - 结算
   - 发票
   - 验收
   - 工作日
   - 分期
   - 税率
   - 上限
   - 账户变更
5. 对候选段打分，保留分数最高的若干条

这个逻辑的目标不是完全理解合同，而是尽量把发送范围压缩到付款相关条款附近。

## 当前怎么脱敏

主要在：

- [contract_llm.js](C:/Users/turui/Documents/Playground_oa_finance_rebuild/oa_finance_audit_rebuild_extension/bg/contract_llm.js)

### 1. 已知字段直替换

会优先把本地已经知道的值替换成 token，例如：

- 合同对方公司
- 付款单收款公司
- 合同收款账号
- 付款单收款账号
- 合同流程号
- 付款单流程号
- 合同标题
- 付款单标题
- 付款金额

### 2. 规则识别替换

然后再对候选条款文本跑规则脱敏，替换这些：

- 附件名
- 单据名
- 邮箱
- 手机号
- 身份证号
- IP
- 日期
- 百分比 / 税率
- 金额
- 银行名
- 长账号 / 长编号
- 一些标签型字段值
- 一些标签后的人名
- 带公司后缀的主体名

### 3. 进一步收缩正文

当前每段候选条款还会：

- 去掉明显敏感行
- 截短到固定长度

## 当前前端会显示什么

当前前端会显示：

- 摘要状态
- 大模型发送状态
- 发送说明
- 发送给 AI 的预览（脱敏后）

其中“发送给 AI 的预览”现在默认收起。

## 当前方案的安全等级

我的判断是：

### 可以说的

- 比“直接发整份合同”安全很多
- 比早期版本安全很多
- 已经适合内部试跑 / 内部验证功能

### 不能夸大的

- 不能定义成“严格保密最终方案”
- 不能定义成“完全满足保密要求”

原因很简单：

- 当前发出去的仍然是“脱敏后的条款片段”
- 不是“纯结构化 facts”
- 规则脱敏永远有漏网风险

## 当前最合理的定位

当前这版应该被视为：

- 内部 MVP
- 可试跑版
- 过渡方案

而不是：

- 最终保密版

## 后续推荐方向

更稳的终态应该是：

1. 本地先抽结构化 facts
2. 外部模型只接收 facts
3. 外部模型只负责展示润色
4. 不再接触原始合同条款文本

也就是：

`本地抽 facts -> 云端模型润色 -> 前端展示`

而不是：

`本地筛原始条款 -> 脱敏后外发`

## 结论

一句话总结：

当前方案已经能支持合同付款摘要的 MVP，但从保密角度看，它仍然只是“脱敏后的条款片段外发方案”，不是最终方案。
