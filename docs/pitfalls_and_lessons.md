# OA 付款审核插件踩坑总结

## 2026-04-15 付款页发票来源如果直接缓存 COS 签名 URL，过一阵再点就会变成 `Request has expired`

- 现象：像 `DDFK-202604070012` 这类付款单，面板里主核对已经是 `pass`，但用户从插件里点击“付款页发票明细”后会打开一条 COS XML 报错页，内容是 `AccessDenied / Request has expired`。
- 根因：`detailInvoiceUrl` 返回的是带 `q-sign-time` 的临时签名 URL。分析时拿到的这条 URL 只有短时有效；旧实现把它原样写进 `analysisJson` 和卡片 `href`，用户晚一点再点，就会命中过期签名。
- 调整：详情页“打开来源”改成点击时先走后台刷新一次发票 URL，再打开新签名；后台按当前付款单 `processCode/detailUrl + sourceName` 重新读取 flowable 详情并匹配对应发票明细。
- 经验：对象存储签名 URL 只能当“瞬时下载凭证”，不能当稳定来源链接长期缓存给 UI。凡是 OA 返回的外链附件如果带签名时间窗，展示层都要把“打开动作”和“刷新凭证”绑在一起。

## 2026-04-15 文档维护：架构变化一旦跨过“串行 -> 异步并行”，README 和方案文档要一起更新

- 结论：像 `requestId` 进度隔离、列表页受控并发、OCR bridge 复用这种变化，不属于“代码细节”，而是已经改变了系统运行方式，必须同步写进 README、文档索引和实施清单。
- 结论：只在 `pitfalls_and_lessons.md` 记经验不够，后续接手的人首先看的通常是根 README 和 `docs/rebuild_plan.md`；如果这两处没更新，大家会继续按旧的串行模型理解系统。
- 结论：当实现已经进入异步并行阶段，文档里要明确写出“哪里并行、哪里隔离、并发数多少、缓存怎么失效”，否则排查线上问题时很难迅速建立正确心智模型。

## 2026-04-14 实施：MV3 里的 OCR 复用要把“池”放到宿主页隔离世界

- 结论：MV3 background 自己不适合直接承载 Tesseract 的图像 OCR 生命周期，但可以把 worker 池放到宿主页 tab 的 `ISOLATED` world，用 background 做初始化、调用和释放编排。
- 结论：如果 OCR 前还需要在宿主页里做 canvas/pdfjs 预处理，最好直接在同一个隔离世界里调用全局桥接对象，避免把大块 data URL 在 tab 和 background 之间来回搬运。
- 结论：批量分析结束时显式释放 OCR 池，空闲时再加一层 idle terminate，是兼顾性能和内存占用的更稳做法。

## 2026-04-14 评审：优先修“误丢数据”和“重型性能瓶颈”

- 结论：像收款账号最短位数阈值、附件候选去重这类逻辑，先判断会不会误删真实业务数据；这类问题优先级通常高于纯结构整理。
- 结论：`analyzePageSnapshot` 顶层多路来源分析虽然适合提速，但不宜直接无脑全量 `Promise.all`，更稳妥的是分组并发或限流并发，避免把 OA 详情页抓取、附件下载和 OCR 同时打满。
- 结论：OCR 这类重型能力的瓶颈不在“识别规则多几条”，而在 Worker 生命周期；反复 `executeScript + import + createWorker + terminate` 会把批量附件分析的耗时放大。
- 结论：`list_page.js` 里的标签/文案映射属于可维护性问题，可以顺手收敛成字典映射，但排期应明显晚于数据正确性和性能问题。

## 2026-04-14 发布前收口：标题文案先做减法，再谈视觉层级

- 结论：如果界面已经进入正式发布阶段，标题区优先保留“产品名 + 当前状态”，像“重构版”这类阶段性标签应该尽早从用户可见入口移除。
- 结论：上下两行标题在窄面板里会放大“头重脚轻”的观感；合并成单行并清掉额外上边距，通常比继续压字号更稳。
- 结论：发布前文案收口不要只改一个面板标题，至少同步检查 `manifest` 名称、初始化提示和其他用户直接可见入口，避免同一产品出现两套叫法。
- 结论：像 `rebuild-phase5-...` 这种构建标签即使对开发有用，也不该直接暴露在正式面板主工具栏；发布态优先隐藏或移到仅调试入口。
- 结论：当工具栏只剩一个主按钮时，优先把它并入标题区或状态区，避免为了单个动作单独占一整行，平白拉高首屏。

这份文档专门记录这轮重构中遇到过的坑、症状、原因、修复方式和后续建议。

## 1. VPN / 代理导致自动化浏览器打不开 OA

### 症状

- 手动浏览器偶尔能开 OA
- 自动化脚本访问 `http://oa.cyou-inc.com/index` 报 `ERR_HTTP_RESPONSE_CODE_FAILURE`

### 原因

- 自动化浏览器仍然走了系统代理或 VPN 代理
- OA 内网地址没有走直连

### 修复

- 在测试脚本里强制加直连参数
- 系统代理补白名单：
  - `oa.cyou-inc.com`
  - `*.cyou-inc.com`
  - `ai.cy.com`
  - `10.*`
  - `<local>`

### 当前策略

- [test_rebuild_single_case.py](C:/Users/turui/Documents/OA_Payment_Audit_Rebuild_Project/scripts/test_rebuild_single_case.py) 已内置绕过代理参数

## 2. OA 页面自己的控制台报错干扰判断

### 常见红字

- `finance.cyou-inc.com` 的 CORS
- `setValue`
- 各种 `micro-app` 报错

### 原因

- 这些大多是 OA 页面自身的微应用错误
- 不是插件自身的主错误

### 教训

- 不要只盯浏览器控制台
- 要优先看插件自己的诊断信息和结果 JSON

## 3. service worker 里跑 pdf.js / OCR 问题很多

### 症状

- `No "GlobalWorkerOptions.workerSrc" specified`
- `Setting up fake worker failed`
- `Worker is not defined`

### 原因

- MV3 service worker 对 `pdf.js` 和 OCR 运行环境不友好
- worker、wasm、动态 import 都容易踩坑

### 修复

- 避免把复杂 PDF/OCR 工作放在 service worker 里硬跑
- 改成在更稳定的上下文里执行 PDF 文本提取和 OCR

## 4. pdf.js 中文 PDF 字体警告很多

### 症状

- `translateFont failed`
- `TT: undefined function`
- `cMapUrl` 相关 warning

### 原因

- 中文 PDF 缺字库/字形映射资源时容易报警

### 修复

- 配置 `cMapUrl`
- 配置 `standardFontDataUrl`
- 降低无意义 warning 对控制台的干扰

## 5. OCR 不能依赖外网语言包

### 症状

- 换一台电脑后 OCR 不稳定
- 首次使用 OCR 要联网

### 原因

- 原始方案默认从外网拉 `tessdata`

### 修复

- 把 `chi_sim` 和 `eng` 语言包放到扩展本地
- 通过 `manifest.json` 暴露本地资源

## 6. 扫描版 PDF 只扫前两页会漏账号

### 症状

- 合同 PDF 肉眼能看到收款账号
- 插件却识别不到

### 原因

- 扫描版 PDF OCR 只扫前两页
- 账号实际在更后面的页里

### 修复

- 短文档多扫几页
- 长文档扫前几页和后几页

## 7. 只靠文件名识别发票完全不够

### 症状

- `vsg_output_xxx.jpg` 这类发票图不被当成发票
- 金额和公司命中了，但来源仍显示合同

### 原因

- 文件名看不出来是发票
- 旧逻辑只按文件名做角色判断

### 修复

- 改成按 OCR / 正文内容识别发票
- 强化发票优先覆盖逻辑

## 8. 付款单字段核实付款单自己是严重偏航

### 症状

- 前端出现“已在付款单字段中核实收款公司名称”之类文案

### 原因

- 付款单字段被错误地当成证据来源

### 修复

- 明确禁止自证
- 付款单字段只做被核验目标

## 9. 缺证据不等于不一致

### 症状

- 发票里没账号时，账号直接报红
- 合同里没账号时，也直接报红

### 原因

- 旧规则把“没提取到”误当成“冲突”

### 修复

- 统一改成黄灯
- 只有发现明确冲突证据才给红灯

## 10. 老 workflow 页面链接不可靠

### 症状

- `workflow.cyou-inc.com` 页面打不开
- 但历史接口有时还能拿到数据

### 原因

- 页面链路和历史 API 权限不是同一套
- `workflow` 域名有时路由本身就不通

### 修复

- 尽量优先走历史接口
- 不把老页面链接当唯一真相来源

## 11. `sourceInstId` 在部分验收页里是必须的

### 症状

- 验收流程链接明明存在
- 但详情页读不出来

### 原因

- 某些流程详情依赖 `sourceInstId`

### 修复

- 保留并传递 `sourceInstId`

## 12. 合同页可读，不代表合同附件已读全

### 症状

- 合同有效期已经出来了
- 但付款条件仍然是“未提取”

### 原因

- 很多时候只是读到了合同页表单
- 没有稳定读到合同附件正文，或正文里没成功提取条款

### 修复

- 新增合同处理状态：
  - 是否进入合同页
  - 发现几个合同附件
  - 成功解析几个
  - 条款来源是表单还是附件

## 13. 合同附件会出现重复和 hash 名

### 症状

- 前端显示合同附件很多
- 但肉眼看到没那么多
- 有些名字是一串 hash

### 原因

- 同一文件可能以多种形式进入候选集
- 有些是物理文件名，有些是人类文件名

### 修复

- 改进去重
- 更偏向保留人类可读文件名
- 前端展示时排掉明显无意义的 hash 名

## 14. 字段映射太宽会把邮箱当银行账号

### 症状

- 合同页里某个字段其实是邮箱
- 却被错误当成账号来源

### 原因

- 账号候选字段过宽
- 没做足够的“像银行账号”的校验

### 修复

- 对账号候选做更严格过滤
- 像邮箱这类值不再进入账号证据

## 15. 图片 OCR 不能只跑整图一次

### 症状

- 发票截图里肉眼能看到金额
- 但插件识别不到

### 原因

- 单轮 OCR 对小字和右下角金额不稳定

### 修复

- 原图 OCR
- 灰度增强 OCR
- 高对比 OCR
- 局部裁切 OCR
- 数字专用 OCR

## 16. 合同摘要不是“多加一层摘要”就结束

### 症状

- 摘要很快能给出付款结论
- 但如果摘要候选范围控制不好，仍然可能混入过长原文
- 用户会直观感觉“这和直接贴合同差别不大”

### 原因

- 早期版本虽然不是整份合同直出
- 但本地筛出来的候选条款还是可能过长
- 仅靠裁切和隐藏并不等于最小披露

### 教训

- “不是整份合同直出”不等于“已经足够安全”
- 要同时控制：
  - 候选条款长度
  - 候选条款内容范围
  - 文本最小化程度
  - UI 是否误把原文露出来

### 当前策略

- 候选条款优先收缩成关键词句子窗口
- 去掉明显的签章区、联系人区、地址区、账户信息区
- 摘要候选默认收起
- 收起后正文不再显示

## 17. 合同区“悬浮原始截图”不是纯前端小功能

### 症状

- 想在付款页的“合同摘要 / 付款条件”区域鼠标悬浮时，直接看到合同原文对应位置的截图
- 直觉上像是补一个 tooltip，但现有结果里主要只有文本摘录、来源名和来源链接

### 原因

- 当前合同链路已经能产出条款候选文本、摘要、来源 URL，但没有稳定产出“原文截图 / 页图 / 定位框 / 裁剪坐标”
- 详情页侧边卡片和列表页弹层都已有 hover / popover 骨架，但它们承载的是文本，不是图片证据
- 如果要做到“看到原始截图就知道这句出自哪里”，通常还要补齐 PDF/图片页渲染、命中条款定位、缓存与悬浮层展示这一整条链路

### 教训

- 先把需求拆成两层，不要一上来就把“悬浮截图”当成一个纯样式需求
- 第一层可以先做“悬浮文本上下文 + 来源页跳转”，这类改动小、价值高、风险低
- 第二层再做“原始截图 hover”，前提是分析结果里先落出可复用的 page preview / image preview / bbox 元数据

### 当前建议

- 如果目标是提升人工复核效率，优先把 hover 挂在“证据条款卡片”上，而不是泛化挂在所有合同摘要字段上
- 如果短期要上线，先做文本 hover；如果要做截图 hover，优先只覆盖合同附件中的 PDF / 图片来源，先不碰复杂 HTML 合同页

## 18. “内置 PDF 阅读器 + 关键词搜索”通常比“悬浮原始截图”更值

### 症状

- 希望用户不下载合同 PDF，也能直接在插件里检索条款
- 同时在想要不要继续做“悬浮原始截图”来辅助人工复核

### 原因

- PDF 阅读器本身有成熟现成方案，优先应该复用官方 PDF.js viewer，而不是自研渲染器
- 只要能拿到附件二进制，就可以走 Blob URL / 扩展页内嵌 viewer 的路线，工程上比“截图定位 + 裁剪 + hover 展示”更直
- 但 PDF 搜索依赖文本层；扫描版 PDF 如果没有文本层，仍然需要 OCR 才能搜到

### 教训

- “能内置阅读器”不等于“所有合同都能直接搜到关键字”
- 对文本型 PDF，内置 viewer 的收益很高；对扫描件，必须明确走 OCR 兜底，不然用户会误以为系统没找到
- 如果资源有限，优先做“扩展内置 PDF.js viewer + 搜索 + 打开来源”，再考虑截图 hover

### 当前建议

- 推荐优先做独立的扩展阅读页或抽屉式阅读器，不要先把完整阅读器硬塞进现有小 hover
- V1 目标应是：打开 PDF、页内搜索、关键词高亮、回到来源链接
- V2 再考虑：基于当前命中条款自动带入搜索词、自动跳页、扫描件 OCR 检索

## 19. 当前读取速度的主要瓶颈不在 UI，而在串行 I/O

### 症状

- 单次分析里会依次读取付款页附件、合同、验收、国内 PR、采购订单
- 命中历史流程或需要抓取关联页快照时，等待会明显变长

### 原因

- 多条关联单据和多份附件目前大量使用串行 `await`
- 关联页快照采集包含固定等待和轮询，慢页会把总时长线性拉长
- 批量缓存读取虽然有入口，但后台仍是逐个 `storage.get`

### 教训

- 想提速，优先优化“后台读取链路”，不要先从前端 hover 或渲染层下手
- 第一优先级通常是：减少固定等待、引入受控并发、提升缓存命中
- OCR / PDF 解析属于重操作，适合按需触发，不适合默认全量预跑

### 当前建议

- P1：把批量缓存读取改成单次批量 `storage.get`
- P1：把互不依赖的合同 / 验收 / PR / 采购订单读取改成受控并发
- P1：把附件扫描从完全串行改成小并发，并保留优先级和数量上限
- P2：收紧 `collectPageSnapshotFromUrl` 里的固定等待与轮询次数

## 17. 规则型文本最小化只能算过渡方案

### 当前能脱的

- 合同名 / 附件名
- 流程号 / 合同号 / 文档号
- 日期
- 邮箱
- 手机号
- 身份证号
- IP
- 金额
- 百分比 / 税率
- 长账号 / 长编号
- 银行名
- 一些标签后的人名和字段值

### 当前仍然不该夸大的点

- 这不是严格保密最终版
- 它更像内部试跑版
- 因为它本质上还是：
  - 本地筛原始条款
  - 再做摘要整理

### 更稳的终态

- 本地先抽结构化 facts
- 不再看到原始条款文本

## 18. 老历史合同页不能只赌附件下载成功

### 症状

- 付款单明明已经关联到了合同页
- 详情页单独审核偶尔还能看到合同信息
- 但批量自动审核里合同经常显示“未提取到明确付款条件”或像是“没抓到合同”

### 原因

- 一部分老历史合同页走的是旧 `workflow/history` 链路
- 这类页面里的附件链接经常是 `10.1.9.119/files/...`
- 这类链接在 `fetch/XHR` 场景下可能返回 200 但空响应体，不能把“拿到 URL”直接等同于“正文一定下载成功”
- 如果分析逻辑只依赖附件正文，而不看合同页本身的字段和正文快照，就会在批量审核里误判成“合同没抓到”

### 修复

- 合同分析改成双路并行：
  - 优先尝试附件正文
  - 同时保留合同页快照兜底
- 即使附件下载不稳定，也会从合同页快照里抽：
  - 合同名称
  - 合同开始/结束日期
  - 付款、支付、结算、发票、验收、自动顺延、续签等关键词附近正文
- 批量审核弹层里，如果付款条款没抽全，也至少展示：
  - 合同期间
  - 合同来源
  防止用户误以为“完全没抓到合同”

### 教训

- 老历史合同页要按“附件正文 + 页面快照”双保险设计，不能单押附件下载
- “合同链接存在”也不等于“合同证据已经足够”，需要看正文质量而不是只看有没有 ref

## 19. 批量审核弹层点了没反应，很多时候是渲染时异常而不是点击没触发

### 症状

- 列表页里点 `通过 / 预警 / 异常` 看起来没反应
- 有时要多点几下
- 控制台里能看到 `ReferenceError`，例如 `firstNonEmpty is not defined`

### 原因

- 这类问题不一定是点击事件没绑上
- 更常见的是点击已经进入了打开弹层逻辑，但弹层渲染过程中抛异常，导致用户体感上像“没点开”

### 修复

- 先查控制台是否有 `renderPopoverBody`、`renderRelatedSummary` 一带的异常
- 缺的小工具函数要补齐，比如 `firstNonEmpty(...)`
- 点击问题排查顺序应该是：
  - 事件有没有触发
  - 弹层有没有创建
  - 渲染函数有没有报错

### 教训

- 列表页交互问题不能只盯事件绑定，渲染期报错也会伪装成“按钮无响应”

## 26. 列表页批量审核和详情页单张审核如果不共用缓存，用户会觉得“明明审过了还要再点一次”

### 症状

- 在待办列表点过“自动审核本页”后，某一行已经显示 `通过 / 预警 / 异常`
- 再点进同一张付款单详情页，侧边栏仍然停在“开始采集”，必须再手动点一次
- 刷新列表页后，刚才跑完的结果也会全部消失

### 原因

- 列表页和详情页原本是两条独立入口
- 列表页结果只存在页面内存态，详情页打开时并不知道刚才已经审过
- 没有统一的缓存层来复用最近一次分析结果

### 修复

- 在扩展后台增加按 `processCode` 存储的自动审核缓存
- 缓存写入点放在统一分析入口，保证列表页和详情页都走同一份结果
- 列表页刷新时先批量查缓存，有命中就直接回填行状态
- 详情页打开时也先查缓存，有命中就直接展示，并标记为最近一次自动审核结果
- 当前缓存 TTL 设为 30 分钟，避免长期复用过期结论

### 教训

- 只做“批量入口能跑”还不够，用户更在意不同入口之间是否连续
- 这类审核结果天然适合做短时缓存，否则既浪费 OA 请求，也会让体验显得重复
- 缓存最好放在后台统一管理，而不是散落在单个页面脚本里各自存一份

## 27. 合同审核场景里，“条款证据包”通常比“单句摘要”更适合作为主展示

### 症状

- 用户看到一句付款摘要后，仍然会继续追问“具体是哪条”“前后文是什么”“有没有例外”
- 当合同里同时出现固定期限、自动续展、订单覆盖等表述时，单句摘要很容易过度简化
- 财务审核更在意证据是否齐全，而不是系统是否给了一个看似明确的结论

### 原因

- 单句摘要天生会压缩信息
- 被压缩掉的往往正是审核最关键的限制条件、前提条件和例外约定
- 合同场景本质上更适合“证据检索 + 人工确认”，而不是“系统代判”

### 修复

- 将合同展示从“Top 1 摘要”升级为“按主题展示 Top N 条款”
- 固定两个主题入口：`付款条件`、`合同期限`
- 每条结果至少展示条款编号、正文片段、页码和命中关键词
- 支持展开上一条 / 当前条 / 下一条
- 对 `但 / 除非 / 前提是 / 自动续展 / 另有约定除外` 等表达做显式提醒
- 同主题下命中多个潜在冲突条款时，提示人工确认

### 教训

- 审核类产品优先级最高的是“可解释”，不是“看起来很会总结”
- 摘要层更适合做辅助整理，不适合替代证据本身
- 对合同这类高语义密度材料，先把条款找准，比直接追求一句漂亮摘要更重要

## 28. 付款条件召回如果只盯“付款 / 发票 / 验收”，会漏掉 KPI / 投放效果类前提

### 症状

- 合同里明明写了“达成 KPI 后结算”“按投放效果结算”“未达标按比例扣减”
- 系统却只召回了“收到发票后付款”或“若干工作日内支付”这类时间型句子
- 用户会觉得系统抓到了付款时点，却没抓到真正的付款前提

### 原因

- 早期付款条件关键词更偏通用采购合同
- 召回词主要围绕 `付款 / 支付 / 发票 / 验收 / 工作日`
- 没把 `KPI / 达标 / 投放 / 曝光 / 点击 / 转化 / 对账 / 扣减 / 补量` 这类效果型条件当成强信号

### 修复

- 在“付款条件”主题下单独加入 KPI / 投放效果类关键词组
- 这类词既参与召回，也参与排序加权
- 当同一主题下同时出现“时间型付款条款”和“KPI 型付款条款”时，直接提醒人工确认

### 教训

- 对财务来说，“何时付款”和“满足什么条件才能付款”同样重要
- 投放、营销、代运营、效果广告这类合同里，KPI 本身就是付款条件，不是背景说明
- 付款条件召回规则必须按合同类型逐步扩展，不能长期只按通用采购逻辑设计

## 29. 联网校验后发现，真实合同高频词往往比“教科书关键词”更有用

### 症状

- 词表里虽然有 `付款 / 支付 / 有效期 / 期限`
- 但一遇到公开招采合同、框架合同、服务外包合同，就容易漏掉真正关键的条款
- 尤其是 `据实结算 / 考核后支付 / 一年一签 / 具体以订单为准 / 自动续展` 这类表达

### 原因

- 早期词表更像法务摘要词表，不够像真实业务合同词表
- 真实合同常混合三种语言：
  - 法务语言
  - 业务执行语言
  - 考核 / 结果 / 订单覆盖语言

### 修复

- 用公开合同和公开招采附件反向校验词表
- 将 `据实结算 / 审核确认 / 结算表 / 考核后支付 / 未达标扣减 / 一年一签 / 自动续展 / 具体以订单为准` 纳入强信号
- 对 `KPI` 类场景，不只搜字面上的 `KPI`，还同步搜 `考核 / 评分 / 达标 / 扣减 / 对账确认`

### 教训

- 关键词设计不能只靠经验，最好拿公开合同做回归样本
- 真正决定召回效果的，往往不是“最正式的词”，而是业务里最常写的词
- 对付款审核这类任务，`据实结算 / 考核 / 扣减 / 订单覆盖` 这类表达必须高优先级保留

## 30. 游戏公司合同类型很杂，付款条件词表如果只按“通用采购合同”设计，迟早会漏

### 症状

- 物业租赁合同里，系统只抓到“付款”却漏掉“自动续展”或“租金 / 物业费 / 水电费”
- 买量投放合同里，系统只抓到“收到发票后付款”，却漏掉“对账确认 / 后台消耗 / KPI / 扣减 / 补量”
- 美术视频外包、软件授权、软著代理、问卷调查这些合同，会各自冒出一套不同的付款前提

### 原因

- 早期规则更像“通用采购合同摘要器”
- 没把游戏公司的真实合同类型拆开看
- 同一个“付款条件”主题，在不同合同类型里的高频词完全不一样

### 修复

- 把合同关键词从单层词表改成“主题词 + 合同类型词 + 限制词”三层
- 明确覆盖：
  - 物业租赁 / 水电物业
  - 买量投放 / 广告代理
  - 美术视频外包
  - 软件授权 / 订阅
  - 软著 / 版权代理
  - 问卷调查 / 用户研究
- 本地摘要里增加“识别到的合同类型”“限制提示”“冲突提示”这些元信息

### 教训

- 同一个功能名叫“合同审核”，不代表背后只有一种合同
- 先按业务类型拆清楚，再设计关键词，命中率会比只扩词表更稳
- 对游戏公司来说，买量和外包类合同的付款前提复杂度，通常高于普通采购合同

## 31. 当本地规则已经覆盖主路径时，先把摘要口径收成单一路径，比“多套口径并行”更稳

### 症状

- 合同摘要一部分来自本地规则，一部分来自别的整理路径
- 用户很难判断当前看到的到底是哪条链路给的结果
- 一旦不同路径口径不一致，前端就会混入“摘要失败 / 回退展示”这类状态噪音

### 原因

- 早期版本存在多条摘要链路并行
- 但后续真实回放表明，当前主要问题集中在本地提取和合同类型覆盖，不在摘要入口数量
- 当本地规则已能覆盖主路径时，继续保留多套摘要路径只会增加边界复杂度

### 修复

- 合同摘要统一改成纯本地规则口径
- 合同摘要入口固定为单一 provider
- 清理源码里的多余摘要分支和误导性文案

### 教训

- 审核类产品要先追求“边界清晰、结果可解释”，再谈摘要层加成
- 当本地链路已经足够支撑主路径时，默认并行多套摘要入口往往不是加分，而是加变量
- 先把产品收敛成纯本地，再决定未来是否要加一个明确可控的辅助层，会更稳

## 18. UI 折叠如果做不好，会把安全感直接打没

### 症状

- 标题写着“摘要候选预览（已裁切）”
- 但下面还挂着原始条款卡片
- 收起后正文没有完全隐藏

### 教训

- 这类 UI bug 不只是样式问题

### 当前策略

- 发送预览做成完整折叠区
- 默认收起
- 收起时内容不展示
- 原始条款不再挂在预览区下面

## 21. 侧边栏只设 `max-height`，不代表用户就一定能滚动

### 症状

- 面板里其实已经渲染出了关联单据和合同摘要
- 但下面一截被截断
- 鼠标滚轮和触控板都滚不下去

### 原因

- 外层容器只有 `max-height`
- 内层卡片没有被压进固定高度
- 结果卡片自己长到了视口外
- 内部滚动区拿不到正确剩余高度，于是浏览器判断“不需要滚动”

### 修复

- 外层容器改成 `top + bottom` 固定高度
- 卡片改成 `height: 100%`
- `.oa-finance-rebuild-body` 作为唯一滚动区

### 教训

- “内容在 DOM 里但看不见”先查布局，不要先怀疑采集失败
- 排查时直接看：
  - `clientHeight`
  - `scrollHeight`
  - `scrollTop`

## 22. 自动化能进 OA，不代表手动浏览器也一定能进

### 症状

- 回放脚本能正常打开 OA
- 人手点 Edge 却打不开，或者很不稳定

### 原因

- 本机系统浏览器代理仍然走 `127.0.0.1:1080`
- 而回放脚本显式加了直连参数，绕开了代理

### 修复

- 增加直连启动脚本：
  - `scripts/open_oa_direct.ps1`
  - `scripts/open_oa_direct.cmd`
- 增加系统代理例外脚本：
  - `scripts/set_oa_proxy_bypass.ps1`

### 教训

- `WinHTTP` 直连不等于浏览器代理也直连
- 遇到“同一台机器、脚本能进、手动不能进”时，优先查系统代理和例外名单

## 23. 补充协议类合同没有直接付款条款，不等于合同信息提取失败

### 症状

- 合同页能打开
- 合同附件也读到了
- 但合同摘要仍然显示“未提取到明确付款条件”

### 原因

- 这类合同常见形态是“补充协议 + 报价单 / 费用表”
- 正文重点在：
  - 新增什么服务
  - 原合同继续有效
  - 合同期如何延续
- 而不是直接出现“付款方式 / 付款条件 / 支付条款”

### 修复

- 在合同分析层增加补充协议回退摘要
- 当显式付款条款抽不到时，优先从附件里补：
  - `按原合同约定执行`
  - `月租 / 月费 / 一次性费用`
  - `服务期 / 自动延期`

### 真实案例

- `DDFK-202602040012`

这张单最终能稳定提到：

- `2.2 本协议未尽事宜，按原合同约定执行`
- `SD-WAN服务（重庆） 10M ¥2,800`
- `月租服务费用`

### 教训

- 对合同摘要来说，“没命中付款关键词”不等于“没有可展示合同信息”
- 补充协议、租赁、框架协议这几类都要防止被误判成“未提取”

## 24. 采购订单供应商字段不能用过宽的兜底标签
### 症状

- 采购订单页面肉眼看供应商名称和付款单收款公司一致
- 系统却把“收款公司与订单供应商”判成异常

### 原因

- 采购订单详情里常常同时出现多个公司相关字段
- 如果直接按 `供应商 / 收款公司 / 公司` 这类宽标签取第一个命中的值，很容易拿到错误字段
- 后面再和付款单收款公司比对时，就会出现“页面看着一致，系统却判异常”

### 修复

- 对采购订单供应商改成“候选值收集 + 优先匹配”
- 先只收集明确的 `订单供应商 / 供应商名称 / 供应商`
- 如果候选里有和付款单收款公司能松匹配上的，优先选它
- 只有明确供应商字段完全没拿到时，才退回页面快照兜底

### 教训

- 公司类字段不能只靠“第一个像公司名的值”来判定
- 采购订单、合同、验收这几类页面都要尽量先走明确业务字段，再做模糊兜底
# 25. 前端频繁显示乱码时，先查源码是否已混入 mojibake，而不是先怀疑浏览器 UTF-8
### 症状

- 扩展前端偶发或频繁出现 `鍥藉唴PR`、`閾炬帴寮傚父`、`未找�?` 这类乱码
- 有些地方不只是显示坏了，连字段提取也开始异常

### 原因

- 不是浏览器把 UTF-8 页面渲染错了
- 是源码里的文案和字段标签已经被错误转码后写回文件，属于 mojibake 污染
- 一旦坏串进入 `analyzer.js` 这类核心文件，既会影响前端展示，也会影响字段匹配

### 修复

- 先全局扫描扩展源码里的典型乱码串，而不是只看页面表现
- 优先修复会直接展示给用户、以及会参与字段提取的字符串
- 对自动修复后的结果再做二次复扫，防止残留 `�` 或被误替换成别的字符

### 教训

- “看起来像编码问题”和“真的是运行时编码问题”不是一回事
- 对这类项目，最危险的是坏串混进业务标签数组，因为那会让抽取逻辑和展示层一起失真

## 32. 合同候选窗适合召回，不适合直接拿来做字段摘要

### 症状

- 合同摘要里“付款条款摘要”把税率、续签、账户变更之类内容一起串进来
- `付款时限` 没抽出来，但正文肉眼明明有 `15个工作日内`
- `账户变更要求` 被误提成“提前三个月书面通知不再续签”

### 原因

- 召回阶段为了不漏条款，会把命中句的前后文一起打成候选窗
- 如果后面的字段抽取继续直接拿整窗，就会把付款句、税率句、期限句混在一起
- OCR 还会把 `15个工作日内` 打断成 `15个；工作日内`，进一步放大误判

### 修复

- 保留“候选窗召回”这一层，不推翻现有关键词策略
- 进入摘要阶段后改成“句级抽取”，为 `付款条款摘要 / 发票条件 / 付款时限 / 账户变更要求` 分别打分
- 对常见 OCR 断裂做轻量修复，例如：
  - `15个；工作日内 -> 15个工作日内`
  - `增值；税 -> 增值税`
  - `受理通知书；电子版 -> 受理通知书电子版`
- `账户变更要求` 不再匹配裸 `书面通知`，必须和 `账户 / 收款 / 开户 / 银行 / 账号` 同时出现

### 真实案例

- `DDFK-202604030018`

修复后这张单的关键字段变成：

- `付款条款摘要：委托方将在收到受托方发出的受理通知书电子版及总费用等额有效增值税专用发票后15个工作日内完成款项支付`
- `发票条件：收到受托方发出的受理通知书电子版及总费用等额有效增值税专用发票后`
- `付款时限：15个工作日内`
- `账户变更要求：未明确`

### 教训

- 召回做“尽量全”，摘要做“尽量准”，两层不要混用
- 合同 OCR 噪声不可避免，但很多问题不是摘要层不够强，而是后处理颗粒度太粗

## 33. 后台已经产出证据数组，不代表用户真的能看到“证据包”

### 症状

- 方案文档里已经写了 `付款条件 / 合同期限 / Top N 候选条款 / 展开上下文`
- 后台 `contract_terms.js` 里也已经有：
  - `paymentClauseEvidence`
  - `termClauseEvidence`
  - `clauseId`
  - `pageLabel`
  - `matchedKeywords`
- 但前端页面上仍然只有几行摘要，看起来像“方案还没做”

### 原因

- 数据层和展示层脱节

## 34. 合同页链接存在，不等于就应该放弃付款页合同附件兜底

### 症状

- 付款单里已经带了合同附件
- 付款页附件正文也已经成功抽出付款条款
- 但最终合同摘要仍然显示：
  - `已进入合同页，但未提取到明确付款条件`

### 原因

- 旧逻辑把“附件兜底”触发条件写成了：
  - 只有 `没有合同链接` 时才启用
- 一旦存在合同链接，即使那个链接指向老 `workflow` 页面、附件解析完全失败，也会强行相信合同页结果
- 结果就是：
  - 合同页是占位文本
  - 付款页合同附件明明已经读到了有效条款
  - 但不会接管最终结果

### 修复

- 先始终计算 `attachmentOnlyContract`
- 再做质量判断：
  - 如果没有合同页，直接用附件结果
  - 如果有合同页，但合同页摘要仍是“未提取到明确付款条件”这类占位文本，而付款页合同附件已经抽到有效条款，则让附件结果接管
- 同时让附件兜底结果补上 `sourceUrl`，优先使用附件原文链接

### 真实案例

- `DDFK-202603030001`

修复前：

- `contractProcessing.pageStatus = read_ok`
- `paymentTerms = 已进入合同页，但未提取到明确付款条件`

修复后：

- `contractProcessing.pageStatus = attachment_only`
- `sourceName = 北京畅游天津办公区维保合同扫描版2025-2026(1).pdf`
- `paymentTerms = 甲方在收到乙方开具的等额有效的增值税专用发票 15 个工作日内付款`

### 教训

- “有入口”不等于“有质量”
- 对老 OA 页面，优先级不应该只看是否存在合同链接，还要看抽取结果是否真的有效

## 2026-04-13 批量审核状态按钮点击不稳定

- 现象：列表页里 `通过 / 预警 / 异常` 按钮有时需要点很多次，甚至完全没反应。
- 根因：状态按钮原来主要依赖 `document` 级 `click` 代理；而列表表格本身会频繁重绘，我们自己的 `MutationObserver`、按钮重建、弹层开关又都在同一条链路里，导致事件时序和节点存活状态都不稳定。
- 修复：把状态按钮点击改成直接绑在按钮元素本身，按钮自己触发 `openPopoverWhenReady(...)` 或 `auditProcessCode(...)`；`document` 级点击只保留“点击外部关闭弹层”。
- 经验：这种高频重绘表格里的交互按钮，优先用元素自身事件，不要把主交互完全压在全局事件代理上。

## 2026-04-13 自动审核缓存改为当天有效

- 现象：之前缓存 `30 分钟`，开发阶段还行，但真实办公场景里，用户同一天内来回切单、刷新列表、再进详情时，会觉得“刚审过怎么又要重跑”。
- 调整：把缓存有效期改成“当天有效”，用 `cachedDay=YYYY-MM-DD` 作为命中条件；同时仍保留 `buildTag` 校验，避免扩展版本变化后继续复用旧结果。
- 经验：列表页/详情页共享结果更接近“同一工作日的审核会话”，当天有效比纯分钟级 TTL 更符合财务使用习惯。

## 2026-04-13 弹层点不开时先看控制台异常

- 现象：状态按钮点击后“像是没反应”，但实际是弹层渲染阶段抛了 `ReferenceError`，导致 `showPopover(...)` 中断。
- 根因：验收单摘要逻辑用了 `firstNonEmpty(...)`，但重构时漏掉了函数定义，点击按钮后控制台直接报错，用户体感就是“点了没反应”。
- 修复：补回 `firstNonEmpty(...)` 工具函数，并把这类共享小函数尽量放在文件顶部集中定义，避免局部重构时漏带。
- 经验：前端交互“无响应”不一定是事件没触发，也可能是渲染函数内部异常；遇到这类问题，先看控制台栈比先猜点击逻辑更快。

## 2026-04-13 老历史合同页附件下载要带授权头并保留兜底

- 现象：像 `DDFK-202604010026` 这种老历史合同页，流程链接明明能打开，附件名也能发现，但合同正文一直提不出来，日志里表现为 `attachmentDownloadedCount=0`、`附件响应为空`。
- 根因：这类附件实际落在 `http://10.1.9.119:2212/files/...` 一类内部文件服务上。后台扩展直接 `fetch` 虽然有 host 权限，但如果不带 OA 页里的授权头，文件服务可能回空内容；只靠发现了附件 URL 还不够。
- 修复：后台直连下载时补带当前 OA 页的 `Authorization / oauthtoken` 等运行时授权头；同时保留页面上下文 `fetch` 作为第二层兜底，避免单一路径失效时整条合同链路直接掉空。
- 经验：老流程合同页的“发现附件”和“成功拿到正文”是两回事。涉及跨域内部文件服务时，下载层必须单独设计授权和兜底，不能把附件 URL 当作已可用正文来源。

## 2026-04-13 详情页浮层 UI 状态不要和审核缓存混用

- 现象：这次详情页侧栏要加“多区块展开/收起、拖动位置、面板宽度”这类纯 UI 能力，如果直接复用现有缓存结构，最容易把详情页视觉状态和批量审核结果、当天缓存命中逻辑搅在一起。
- 风险：列表页批量审核和详情页共用的是“审核结果缓存”，它要保证 `processCode`、`cachedDay`、`buildTag`、结果体结构稳定；而侧栏 UI 状态是用户个人偏好，刷新和切单时只应该影响展示，不应该影响审核结果口径。
- 做法：详情页单独使用 `oa-finance-rebuild-detail-panel-ui-v1` 存 `width / top / openSections`，并在内容脚本内部自行读写、clamp 和回放；审核结果继续走原有 `oa-finance-rebuild-get-cache / analyze-page` 协议，不改 key、不改 TTL 语义、不改结果结构。
- 经验：共享缓存负责“业务结果复用”，UI 状态负责“界面偏好记忆”。这两层一旦混用，最先出问题的通常不是详情页，而是列表页批量审核的命中、回填和状态按钮一致性。

## 2026-04-13 工作台式详情面板不要靠灰影和分离浮层造层级

- 现象：详情页右侧侧栏拆成 `rail + panel` 两块独立浮层后，虽然功能更全了，但视觉上很容易出现“大块灰影”“一整条灰柱”“像两张卡片压在页面上”的感觉。
- 根因：层级主要靠大阴影、浅灰渐变头部、两栏留白和多个小卡片叠出来；一旦主面板收起，只剩导航时还会保留整列高度，空白区域会进一步放大“灰底感”。
- 调整：把 rail 并进主工作台，改成一个整体容器；静止态只保留很轻的边框和阴影，拖动/改宽时再临时增强反馈；panel 收起时让容器也缩成紧凑条，不再保留整列空柱。
- 经验：产品工作台的层级优先靠布局、留白、对齐和字重来建立。把所有装饰阴影拿掉后，如果界面就散了，说明结构本身还没站住。

## 2026-04-13 只剩导航时要单独做 rail-only 视觉态

- 现象：即使主面板已经收起，如果 workbench 和 rail 仍保留浅灰底、边框或分隔线，用户看到的还是会是一条“灰色边缘”或“灰柱”。
- 根因：展开态和收起态共用同一套容器表面样式，导致收起后仍然继承了工作台底板。
- 调整：`rail-only` 状态下把 workbench 改成透明、隐藏分隔线和 resize handle，只保留导航按钮本身。
- 经验：收起态不是“展开态宽度变窄”这么简单，而是应该有单独的视觉语义；尤其是侧边导航，收起后优先保留按钮，不要保留容器底板。

## 2026-04-13 收起态如果问题反复，优先拆成独立 DOM 而不是继续叠覆盖样式

- 现象：有些视觉残留看起来像“某个颜色没改干净”，但实际上是收起态和展开态仍共享同一个容器结构。
- 根因：只靠 `is-rail-only` 的覆盖样式去抵消展开态的底板、边框、阴影，后续很容易被其他规则、媒体查询或结构变化重新带回来。
- 调整：把收起态直接渲染成独立的紧凑导航 DOM，只保留需要的按钮和拖动入口，不再复用展开态 workbench。
- 经验：当一个状态的视觉语义已经和正常状态完全不同，就不要继续共用一套容器；拆 DOM 往往比继续叠 CSS override 更稳。

## 2026-04-13 固定根节点尽量不承载视觉表面

- 现象：右侧浮层/导航经常会莫名多出“灰边”“底板”“残留背景”，看起来像阴影没清干净。
- 根因：固定定位的根容器、工作台容器、导航容器都同时带了背景或边框，收起态时哪怕只漏掉一层，也会留下整条残影。
- 对比：`D:\\OA-helper` 这类实现里，固定根节点本身几乎不承担视觉表面，真正有底色和边框的只有实际显示的卡片。
- 经验：做右侧悬浮 UI 时，优先让根节点只负责定位；谁真正显示，谁再拥有背景和边框。这样收起态最不容易留下“灰边”。

## 2026-04-13 内容脚本根节点标签类型也会影响残留样式

- 现象：内部容器都已经改透明了，收起态仍然像有一层浅灰底板罩着。
- 根因：内容脚本根节点如果用 `aside` 这类语义标签，宿主页面可能已经有全局样式命中了它；这样即使我们把内部容器拆干净，外层也可能继续带着背景、边框或内边距。
- 对比：`D:\\OA-helper` 的浮层根节点用的是普通 `div`，再配合显式的根层 reset，宿主样式更难漏进来。
- 经验：做嵌入式浮层时，优先用普通 `div` 做根节点，并在根层显式清空 `background / border / box-shadow / padding`。不要默认相信宿主页面不会给 `aside`、`section` 之类标签上样式。

## 2026-04-13 办公工具型精致感来自统一缩尺，不来自大圆角和大胶囊

- 现象：面板功能都齐了，但只要 `24px` 级 padding、`18-28px` 圆角、宽胶囊按钮、厚卡片同时出现，界面就会显得松、笨、像 demo，而不是日常办公工具。
- 对比：`D:\\OA-helper` 这类更顺眼的内部工具，往往不是“设计更花”，而是尺寸更克制：`10-12px` 级内边距、`10-14px` 级圆角、小按钮、小状态 badge、字段块优先。
- 调整：导航、标题、按钮、区块、状态行、字段块要一起缩一档；不能只缩一个按钮或只减一个圆角，否则整套比例还是不对。
- 经验：工具型界面的精致感，本质上是尺寸体系一致。真正决定气质的通常不是颜色，而是 spacing、radius、字号和控件高度是否属于同一套语言。

## 2026-04-13 头部动作区不要拆成两套布局

- 现象：标题右侧的 `拖动 / 状态 / 全部收起` 如果分散在不同 flex 容器里，很容易出现一个按钮浮在上面、另外两个控件掉下一行，视觉上像没对齐。
- 根因：同一组动作被拆进了 `head-main` 和 `head-side` 两套布局规则里，宽度稍一变化就会错位。
- 调整：标题单独一列，所有动作统一放进右上角一条 action row，并统一控件高度和对齐方式。
- 经验：同一语义层的动作必须共用一个布局容器。对齐问题很多时候不是 margin 没调对，而是 DOM 分组本身就错了。
## 2026-04-13 创建 Skill 时先校验 UI 元数据长度

- 现象：用 `skill-creator/scripts/init_skill.py` 初始化新 skill 时，如果传入的 `short_description` 超过长度限制，脚本会先创建 skill 目录和 `SKILL.md`，然后在生成 `agents/openai.yaml` 时失败，留下半初始化状态。
- 根因：`generate_openai_yaml.py` 对 `short_description` 有严格校验，长度必须在 `25-64` 个字符之间；但初始化脚本是在创建目录之后才调用这个校验。
- 调整：创建 skill 前先把 `display_name / short_description / default_prompt` 想清楚，尤其先把 `short_description` 压到 25-64 字符内；如果初始化失败，也要立刻补齐 `agents/openai.yaml` 并重新跑 `quick_validate.py`。
- 经验：脚手架脚本不一定具备事务性。只要创建流程分多步，任何中途校验失败都可能留下“看起来存在、实际不可用”的半成品目录，后续最好马上做一次完整验证。

## 2026-04-13 OA 付款页里的 `PR选择` 不是 `PR单号`

- 现象：排查付款单关联 PR 时，页面上同时出现 `PR选择` 和 `PR单号`，很容易把 `PR选择` 误认成真正的 PR 编号。
- 根因：`PR选择` 展示的是用户在控件里选中的国内 PR 流程标题或名称，真正的流程编码在独立字段 `PR单号` 里；样本里通常表现为 `GNPR-...`。
- 证据：项目文档已确认 `formtable_main_154_dt1` 对应国内 PR，审批意见区也会出现 `PR单号及相关流程：GNPR-...`；现有样本还能看到 `label=PR选择` 时对应值是流程标题，而 `label=PR单号` 才是 `GNPR-202601140008` 这类编号。
- 经验：遇到 `PR选择 / 相关流程 / PR单号` 同时存在的页面，展示名用于给人看，真正用于关联、检索和规则判断的应优先取 `PR单号`，不要把占位文案或流程标题当成编号。

## 2026-04-13 关联流程编号提取必须做格式校验，不能只取首个命中值

- 现象：国内 PR、采购订单等关联页里，字段提取虽然命中了 `流程编号 / 单号` 这类标签，但结果会落成 `流程标题` 这样的占位文本，前端最终把假值展示成真实编号。
- 根因：旧逻辑是“找到第一个匹配标签的值就返回”，没有再校验它是否真的像流程编码；而 OA 页面里同一标签区域常常会先出现表头文本、选择控件文案或说明文字。
- 调整：流程号提取改成候选集模式，先收集同标签下的多个候选，再按业务前缀优先匹配，比如国内 PR 优先 `GNPR-...`、采购订单优先 `CYNCDD-...`，同时过滤 `流程标题 / PR选择 / 相关流程` 这类占位值。
- 经验：凡是“编号类字段”都不能只依赖标签命中，还要叠加格式校验。对 OA 这种表单表头、子表、控件文案混在一起的页面，先验格式再落值，比继续加更多模糊标签安全得多。

## 2026-04-14 清理未引用模块和历史备份前先验真实引用关系

- 现象：仓库里同时存在未引用的 `contract_llm.js`、历史备份 `analyzer.js.bak_20260410_1108`、根目录打包 zip，以及几处仍写着旧工作区的文档链接，看起来都像“可以一起删掉”的残留。
- 根因：这里混着两种情况。一类确实是试验分支和打包产物残留；另一类只是扩展多运行时隔离带来的重复实现，比如 background 侧工具和 content script 侧工具并不能简单合并。
- 调整：清理时先做全局引用校验和运行时边界校验，只删除未引用文件、未使用权限和误导性文档，不把多运行时隔离层误当成重复设计直接收掉。
- 经验：做仓库减重时，优先验证“有没有真实调用”和“是不是同一运行时职责”。名字相似不等于可以合并，未引用才是真正的低风险清理入口。
## 2026-04-14 详情面板里的 hover 提示不要被 section 容器裁掉

- 现象：主核对或关联单据卡片上的悬浮说明已经渲染出来了，但只要提示层超出当前 section 的底部，就会被下面的区块边框直接截断，看起来像“信息被遮住了”。
- 根因：hover 提示使用的是卡片内的绝对定位浮层，而外层 `.oa-finance-rebuild-panel-section` 为了卡片圆角使用了 `overflow: hidden`；这样浮层一旦越过 section 边界，就会被父容器裁剪。与此同时，下一个兄弟 section 还会在视觉上压住当前 hover。
- 修复：展开态 section 改为 `overflow: visible`，只在折叠态保留 `overflow: hidden`；同时给 hover 中的结果卡片和关联单据卡片抬高 `z-index`，让悬浮说明能盖过下面的 section。
- 经验：只要是“卡片内 absolute/fixed 浮层”的设计，就不要默认把最近的分组容器写成 `overflow: hidden`。如果确实要保留裁剪，最好把浮层挂到更高层，或者至少给展开态单独放开溢出和层级。
## 2026-04-14 仅主核对展开时不要继续套用“多 section 共存”骨架

- 现象：当右侧详情面板只展开“主核对”时，虽然功能没问题，但主内容只占到面板中间一块，右侧和下方会留下明显空白，视觉上像“只用了 60% 的区域”。
- 根因：之前的工作台布局默认按“多个 section 同时存在”来组织，`overview` 只是一段普通 section 内容；当 `openSections` 只剩 `overview` 时，界面仍沿用原来的纵向骨架，没有把空出来的版面重新分配给主核对和辅助摘要。
- 修复：把“仅展开主核对”单独视为 `overview-solo` 展示态，主区展示实时进度和三项主核对，侧边复用已有 `pageSummary / paymentTarget` 做采集概览；其余 section 保持折叠入口，但压缩成紧凑条，不再抢版面。
- 经验：折叠式工作台只要允许“单区独占”，就不要默认共享多区并存的骨架。单区独占时应该切成独立布局，否则很容易出现功能完整但版面发空、用户主观觉得“不饱满”的问题。
## 2026-04-14 固定浮窗如果同时被 `top` 和 `bottom` 约束，拖动很容易假装成“改高度”

- 现象：详情面板右上角的“拖动”按钮看起来像是在拖窗口位置，但实际只会改变面板上下占用范围，用户体感是“拖不动窗口，只是在拉高度”，而且高度调节也不直观。
- 根因：根节点原来是 `position: fixed` 且同时绑定了 `top + bottom`，拖动逻辑又只改 `top`；在这种约束下，元素不会真正移动，而是优先改可用高度。结果就是“拖动”和“垂直缩放”被混成同一种行为。
- 修复：改成显式维护 `top + right + height` 三个 UI 状态。拖动时同时更新 `top/right` 来移动窗口位置；横向缩放继续走左侧把手；纵向缩放单独增加底部把手，只更新 `height`。
- 经验：做固定悬浮工作台时，拖动、横向缩放、纵向缩放最好各有独立状态和把手。只要还保留 `top + bottom` 这种双锚点布局，任何“拖动顶部”的实现都很容易退化成“改高度而不是移动位置”。
## 2026-04-14 关联单据卡片要把“概览高度”和“详情信息”分层

- 现象：关联单据区里的 PR、采购订单、验收单卡片会因为摘要长短不一出现高度参差，用户扫一眼时先看到的是版面起伏，而不是状态和标题。
- 根因：卡片此前按正文自然高度撑开，长摘要直接在概览层完整展开，没有把“概览卡片”和“悬浮详情”拆开处理。
- 调整：统一关联单据卡片高度，按采购订单卡片高度的 1.2 倍作为固定展示高度；正文信息做裁剪，底部来源链接贴底，详细字段继续交给 hover 展示。
- 经验：列表型概览区优先保证节奏一致和状态可扫读，长文本不要抢占卡片高度；如果已经有 hover / 二级详情承接信息，就让概览层先服务“快看”，详情层再服务“看全”。
## 2026-04-14 固定高度卡片不能直接对外层做 overflow hidden

- 现象：关联单据卡片统一高度后，鼠标移上去原本应该出现的 hover 详情突然不见了，用户看起来像“悬浮功能失效”。
- 根因：hover 详情层本身就是挂在卡片内部、通过绝对定位浮到卡片外侧的；如果把卡片外层直接设成 `overflow: hidden`，悬浮层会在刚超出边界时被一起裁掉。
- 调整：卡片外层保留固定高度但改回 `overflow: visible`，再单独增加正文内容容器承接 `overflow: hidden`，把“正文裁剪”和“hover 浮层”拆开。
- 经验：凡是卡片里带有 absolute/floating 详情层的场景，裁剪应该落在正文容器而不是最外层卡片；否则视觉上像是在“收文本”，实际连交互层也一起切没了。
## 2026-04-14 拖动入口要用“位置暗示”而不是普通按钮文案

- 现象：详情面板头部把 `拖动 / 状态 / 全部收起` 都做成同一排按钮后，虽然功能齐，但用户会把“拖动”理解成普通操作按钮，而不是窗口手柄；同时“全部收起”占着标题区，会稀释主标题层级。
- 调整：把拖动入口改成面板顶部中间的小横杠，只保留拖动语义，不再和业务动作抢同一视觉层；把 `全部收起` 挪到左侧 section rail 底部，归入“导航控制”而不是“标题动作”。

## 2026-04-14 云存储签名发票图没加 host 权限时，OCR 会整条失效

## 2026-04-14 PDF OCR 拼接与发票 OCR 预处理要按整条链路修

- 现象：PDF OCR 如果把多页文本拼成字面量 `\\n`，后续金额、公司名、账号匹配会一起受影响；图片 OCR 如果只靠固定右下角裁剪、不过滤低置信度结果、也不去掉红章，发票金额和票头识别会同时变脆。

## 2026-04-15 `executeScript` 注入函数不能依赖模块作用域 helper

- 现象：单案 `DDFK-202604070012` 里付款页已经发现 2 个合同附件，分别是 `2015年顺丰合同.pdf` 和 `OA合同归档截图（顺丰）.jpg`，但面板仍显示“扫不到合同”。调试结果里 4 个附件都下载成功，但 `referenceEntries = 0`、`contractProcessing.attachmentParsedCount = 0`。
- 根因：`ocr_bridge.js` 用 `chrome.scripting.executeScript` 把 OCR bridge 注入页面后，注入函数内部调用了模块作用域的 `extractRecognizedText`。`executeScript` 只会序列化目标函数本身，不会把外层 helper 一起带进页面上下文，所以附件解析阶段稳定报 `ReferenceError: extractRecognizedText is not defined`。
- 调整：把 OCR 结果整理 helper 内联到 `bootstrapOcrBridgeInPage` 作用域内，让注入后的 bridge 在页面执行时自包含。
- 经验：凡是传给 `executeScript` 的函数，都要按“可单独序列化执行”来写。除了显式参数外，不要依赖模块外层的 helper、常量或闭包状态，否则会出现“本地看起来已定义，但页面运行时未定义”的隐蔽故障。

## 2026-04-15 已办列表点批量审核失败，不一定是分析失败，而是待办反查前置失败

- 现象：在 OA `已办` 列表点击“自动审核本页 / 批量审核”后，行状态直接显示 `不支持`，弹层里的失败说明是“没有在待办列表里反查到这张付款单”。
- 根因：列表页自动审核入口当前不区分 `待办` 和 `已办`，都会先调用 `/cyouNeiOaServer/flowable/process/todoList`，再用 `processCode` 反查 `procInsId / taskId / procDefId` 去拼详情页链接；`已办` 单据天然不在 `todoList` 里，所以在真正进入分析器之前就会返回空记录并被标记为 `unsupported`。
- 调整：排查这类问题时，先区分是“反查不到列表元数据”还是“详情页分析失败”。前者属于列表入口适配问题，不该误判成审核规则或 OCR 出错。
- 经验：只要列表页审核链路还依赖 `todoList` 反查，就只能天然覆盖待办场景；如果要支持 `已办`，要么改成基于当前表格行直接抽取并拼详情入口，要么补一条专门面向 `已办` 的历史列表反查接口，不能把两种列表当成同一数据源。

## 2026-04-15 小图发票 OCR 拿不到票面类型时，要用页面税额字段兜底专票

- 现象：像 `DDFK-202604070012` 这种顺丰小额快递票，付款页结构化发票明细能命中金额、公司和税额，页面也明确是 `增值税发票`、`关联发票是否正确=正确`、`有效抵扣税额=1.61`，但因为发票图片很小，OCR 没抓到标题里的“增值税专用发票”，结果整单卡在“票面类型未识别”。

- 调整：新增页面字段兜底规则。只有当 `pageInvoiceLabel=增值税发票`、`linkedInvoiceCorrectness=正确`、`deductibleTaxAmount>0` 三个条件同时满足时，才把未识别票种推断成 `增值税专用发票`，并在 `invoiceTypeCheck.snippet` 里显式写出“票面类型来源：页面字段兜底”。
- 经验：发票票种不要只押宝 OCR 标题；在 OA 付款页里，`有效抵扣税额>0` 本身就是很强的专票业务信号。对这种“页面结构化字段已经足够明确、但附件 OCR 因尺寸失败”的场景，应该优先补窄口径业务兜底，而不是一味继续堆 OCR 变体。
## 2026-04-15 合同详情链接里的 `sourceInstId` 被本地正则截断时，会伪装成“没有权限查看该流程”
- 现象：像 `DDFK-202604080005` 这种付款单，人工点击合同链接可以正常进入 `workflow/process/detail/<合同id>?sourceInstId=<付款单id>`，但插件侧合同分析却报“合同页读取失败：没有权限查看该流程”。
- 根因：OA 明细接口 `flowFormData.formtable_main_154_dt4[*].htlink` 返回的合同链接本身就是完整的，真正丢数据的是本地 `PROCESS_LINK_RE`。该正则写在 JS regex literal 里，却把空白字符写成了 `\\s`，于是查询串一遇到 `sourceInstId` 的字母 `s` 就在 `?` 后被截断，最终只剩下 `.../detail/<合同id>?`。
- 调整：把 `PROCESS_LINK_RE` 中的 `\\s` 改回 regex literal 正确写法 `\s`，并补一条回归校验，确保 `parseProcessRef / extractKnownRefs / discoverProcessRefs` 都会保留完整的 `sourceInstId` 查询串。
- 经验：当插件提示“没有权限查看该流程”，先核对原始 `htlink` 与插件内部保存的 `detailUrl` 是否一致；如果 OA 原始链接能打开、插件请求却失败，优先怀疑本地链接提取或拼接把上下文参数吃掉了，而不是真权限缺失。

## 2026-04-15 发票识别已通过时，`pageAttachmentAnalysis = null` 不等于“没有跑到发票 OCR”
- 现象：像 `DDFK-202604030026` 这种付款单，用户侧可能还看到“发票识别有问题”，但 fresh 单案结果里 `invoiceTypeCheck` 已经是 `pass`，同时 `pageAttachmentAnalysis` 却是 `null`，容易让人误以为附件 OCR 根本没执行。
- 根因：这类单据的发票证据不是走“页面附件分析”链路，而是直接来自 `invoiceStructuredSources[*].attachment/sourceUrl` 指向的票面附件。识别结果会直接落进 `invoiceTypeCheck.invoiceTypeRaw` 和 `evidencePool.invoiceStructuredSources`，所以即便 `pageAttachmentAnalysis` 为空，发票 OCR 也可能已经成功。
- 经验：排查“发票没识别”时，不要只盯 `pageAttachmentAnalysis`。先看 `invoiceTypeCheck.status / invoiceTypeLabel`，再看 `evidencePool.invoiceStructuredSources[*].sourceUrl`、`invoiceTypeRaw` 和 `snippet`；如果 fresh 重跑已经是 `pass`，更常见的是浏览器还停在旧扩展、旧 service worker 或旧分析结果。

## 2026-04-15 发票/合同逻辑修了但浏览器还在显示旧结论时，先检查 `BUILD_TAG` 是否同步抬版本
- 现象：像 `DDFK-202604030026` 这种单据，fresh 单案重跑已经能识别出 `增值税专用发票` 且金额/公司/账号全通过，但浏览器详情页面板仍然展示旧 hover 文案，例如“页面显示：未识别”或“请确认发票类型”。
- 根因：详情页 `content.js` 打开时会先通过 `oa-finance-rebuild-get-cache` 读取 `chrome.storage.local` 的缓存分析结果；后台 `background.js` 只按“当天 + `BUILD_TAG` 一致”判断缓存是否有效。如果我们修了分析逻辑却没同步更新 `bg/analyzer.js` 里的 `BUILD_TAG`，同一天跑出来的旧分析缓存就会继续命中，看起来像“代码没生效”。
- 调整：只要分析口径发生了会影响用户结论的变化，就同步抬高 `BUILD_TAG`，让旧缓存自动失效并强制页面重新走新逻辑。
- 经验：这类问题不要只盯 service worker 有没有 reload；如果 fresh 回放和浏览器展示不一致，而且差异正好是旧逻辑文案，优先检查缓存失效条件里是否漏了版本升级。
## 2026-04-15 Word 合同正文提取不能把批注/修订层当成正文

- 现象：合同附件是 `docx` 时，付款条款里明明已经改成 `76500`，但侧边栏合同摘要还会把批注/修订里的 `40000` 一起识别进去，导致付款条件摘要混入“删除值”。
- 根因：旧逻辑直接把 `word/document.xml`、页眉、页脚整段 XML 去标签后拼成文本；这样 `w:del / w:delText` 这类修订删除内容虽然对正文不可见，仍会作为普通文本落进提取结果。
- 调整：`docx` 提取改成只读取 WordprocessingML 里的可见正文节点 `w:t`，同时显式剔除 `w:del`、`w:moveFrom`、`w:instrText`、`w:commentReference/commentRange` 等隐藏层标记；并补了一个回归脚本，验证 `comments.xml` 和删除修订里的 `40000` 都不会再进入合同摘要。
- 经验：处理 Office XML 不要偷懒用“整段去标签”当正文抽取，尤其是合同、发票这类会带批注和修订的业务附件。优先做“可见正文白名单提取”，比事后在规则层过滤脏值稳得多。

## 2026-04-15 本地分发 Chrome 插件时，zip 根层级必须就是扩展根目录

- 现象：插件源码可以直接加载，但打包给别人安装时，如果把外层项目目录或空壳目录一起压进去，用户在 `chrome://extensions` 里加载后会看到“清单文件缺失或不可读”；如果为了减小包体删掉 `node_modules`，PDF、OCR、表格和 Office 附件解析会在运行时缺依赖。

- 经验：本地分发扩展时不要把“源码仓库压缩包”和“可加载扩展包”混为一谈。只要还没有构建产物目录，压缩清单就必须跟 manifest 和运行时引用保持一致；教程里也要直接告诉用户不能加载 zip，必须加载解压后的扩展根目录。

## 2026-04-15 扫描 PDF 里的账号不能只靠整页 OCR

- 现象：`DDFK-202604070002` 的“租金通知单 - 畅游天下.pdf”肉眼可见 `账号：645422386`，但插件只识别出少量乱码和“扫描全能王”，导致收款账号核对停在预警。

- 调整：PDF OCR 增加账号区域裁剪、局部放大和数字模式识别，把中部账号区作为补充 OCR 结果拼回附件文本；同时抬高 `BUILD_TAG`，让旧缓存失效。

- 调整：附件扫描接收已知结构化发票命中结果作为早停条件；合同附件同批存在时优先扫描 PDF，合同截图延后。重跑该单从约 170 秒降到约 86 秒，并保持三项主核对全通过。

## 2026-04-15 公盘更新插件要同步整套运行时核心文件

- 现象：公盘只覆盖 `analyzer/common/extract` 后，用户点击“开始采集”停在“准备开始 / 正在采集当前页面基础信息”，没有继续出现“正在读取付款单”等后台进度。
- 根因：MV3 service worker 会把 `background.js -> analyzer.js -> extract.js / ocr_bridge.js` 作为一组模块加载；只更新部分文件容易形成“分析器新、OCR bridge 或列表入口旧”的混合版本，再叠加浏览器 service worker 缓存，会表现为后台没有正常接管分析请求。
- 调整：公盘更新改为同步 `background.js/content.js/list_page.js/styles.css/bg/*.js/page/collector.js/shared/*.js` 这组运行时核心文件，并用 SHA-256 校验公盘与本地一致；随后用公盘路径作为 `--load-extension` 跑真实单案确认能完成。
- 经验：共享盘分发不是补丁式复制。只要涉及后台模块、OCR、采集或列表页任一处变更，就按核心文件清单整套覆盖，并要求用户在 `chrome://extensions` 点刷新，必要时移除后重装，避免旧 service worker 和新文件混跑。

- 现象：列表页批量审核主观上偏慢时，代码层面最可疑的不是某个单独规则，而是多个流程同时触发附件下载、OCR、隐藏标签页采集和 UI 刷新。
- 排查：重点检查了 `list_page.js` 的批量并发、`bg/analyzer.js` 的分析入口、`bg/io.js` 的页面采集与 `bg/ocr_bridge.js` 的 OCR worker 生命周期，发现结构化发票明细仍会回流到附件 OCR 队列，且并发分析共用同一个页面 OCR bridge 和模块级运行时上下文。
- 经验：性能问题要先把“能否直接用结构化字段”“是否重复 OCR 同一附件”“并发任务是否共享可变全局状态”“进度刷新是否整表重绘”四件事分开看。能用接口字段的证据不要再丢回 OCR，能缓存的附件文本不要按付款单重复解析，共享 worker 必须有引用计数或任务级隔离。

## 2026-04-15 扫描提速修复要同时保护正确性和 UI 稳定性

- 调整：OCR bridge 改成按宿主页 tab 做引用计数，批量并发下最后一个分析任务结束时才释放 worker；结构化发票字段足够时不再默认把票面图片送入附件 OCR；验收关联页先读接口详情，只有接口失败才打开隐藏页；列表进度改成行级刷新，避免每条进度整表重绘。

## 2026-04-15 公盘版 fresh 通过但用户窗口仍预警时，先切断详情页自动缓存回放

- 现象：`DDFK-202604070012` 用公盘路径和全新 Edge profile 重跑已经是金额、收款公司、收款账号三项 `pass`，但用户复用先前打开的 Edge 窗口点击“开始采集”仍看到预警。

## 2026-04-15 批量审核和单独审核结果不一致时，先检查是不是批量链路丢了“页面字段上下文”

- 现象：同一张付款单，在列表页批量审核显示 `预警`，点进详情页后单独审核却是 `通过`。
- 根因：详情页单独审核走的是“当前页面 DOM 快照 + OA 详情 API”，能拿到页面上的 `发票类型 / 关联发票是否正确 / 有效抵扣税额`；列表页批量审核原先走的是“只有详情 URL + OA 详情 API”，如果结构化发票明细里没有直接给出专票类型，就会缺少这组页面上下文，最终把本应 `pass` 的单据打成 `warn`。
- 调整：页面票型上下文不要只依赖 DOM。批量链路在没有 `fieldPairs/bodyText` 时，要继续从 `flowFormData` 补齐：
  - 用 `fplx` + 表单选项映射回页面发票类型；
  - 用 `fpsfzq` + 表单选项映射回“关联发票是否正确”；
  - 用 `fpSubform[*].yxdkse` 回推“有效抵扣税额”。
- 经验：凡是“列表页批量”和“详情页单个”共用同一套规则时，都要先核对两条链路拿到的数据面是不是一致；如果单个路径多拿了一层页面态字段，批量路径就很容易出现看起来“玄学”的误报。

## 2026-04-15 列表页批量已有结果但详情页显示“待采集”时，先查是不是没有把缓存回放标记带过去

- 现象：列表页批量审核已经显示 `通过/预警/异常`，但从列表点进付款详情页后，侧栏状态又回到 `待采集`。
- 根因：此前为了避免详情页自动回放旧缓存，`content.js` 只在 URL 显式带 `oaAuditUseCache=1` 时才读取当天缓存；而列表页原生详情链接和插件补出来的详情链接如果没带这个参数，就会出现“列表命中缓存、详情页却不回放”的割裂感。
- 调整：列表页构造详情链接时统一补上 `oaAuditUseCache=1`，并把表格里原生的 `/workflow/process/detail/...` 链接也改写成带缓存回放标记的版本，这样从列表跳详情时会优先回放同一天、同 `BUILD_TAG`、同缓存 schema 的结果。
- 经验：防旧缓存和保证列表/详情一致性要分开处理。详情页不一定要对所有入口都默认自动回放缓存，但凡是“从列表审核结果继续点进详情”的入口，都应该显式把缓存回放意图带过去。

## 2026-04-15 从列表切进付款详情页要兼顾“脚本注入”和“自动采集”，不然用户会误以为必须先 F5 再点开始采集

- 现象：从 OA 列表里点进采购付款单个详情页时，悬浮插件不出现；只有手工 `F5` 后内容脚本才挂上来，而且挂上来后还要再点一次“开始采集”。
- 根因：`content.js` 只通过 manifest 注入在 `workflow/process/detail/*` 首次文档加载时生效；OA 列表到详情常走单页路由切换，URL 变了但没有整页刷新，所以详情内容脚本不会自动重新注入。与此同时，详情页原逻辑默认只展示面板，不会在进入付款单页后主动开跑分析。
- 调整：列表页常驻脚本要监听 `pushState / replaceState / popstate / hashchange` 和 DOM 变化，在路由切到详情页时主动通知后台补注入 `shared/models.js + shared/evidence.js + page/collector.js + content.js`；详情页面板自身还要支持 `route-change / unmount`，并在命中付款单流程号后等待页面字段稳定后自动触发一次采集。
- 经验：遇到“必须 F5 才出现插件”的问题，优先怀疑内容脚本注入时机，而不是 UI 渲染本身。对 SPA 型 OA 页面，光靠 manifest `matches` 不够，列表常驻脚本或全局详情控制器必须能跟着路由切换补注入和重置状态。

## 2026-04-16 批量审核缓存不能只靠详情 URL 参数回放

- 现象：列表页批量审核已经产出了结果，点进单张付款详情后，侧栏仍然停在“待采集”，看起来像没有缓存。
- 根因：批量结果按付款流程号写入 `chrome.storage.local`，但详情页原先主要从 URL query 里的 `processCode` / `oaAuditUseCache=1` 判断是否读取缓存。OA 的列表到详情经常走 SPA 路由或只有数字实例 ID 的链接，URL 里没有付款流程号时，详情页就不会去按流程号查缓存。
- 调整：详情页自动流程改成先等页面字段稳定，尤其在 URL 没带付款流程号时，使用页面快照里的 `paymentTarget.processCode` 识别 `DDFK/GNTYYFK`，再优先读取当天、同 `BUILD_TAG`、同缓存 schema 的结果；后台缓存键也统一用大写流程号存取，避免大小写导致批量写入和单页读取错位。
- 经验：列表/详情共享缓存时，URL 只能算入口线索，不能当唯一业务标识。只要页面正文已经能识别流程号，缓存回放和自动分析都应该能以“页面事实里的流程号”兜底，再用显式回放标记、版本、日期、schema 限制 stale cache 风险。

## 2026-04-16 详情页入口不能只依赖悬浮面板 root 自己出现

- 现象：从 OA 列表或外部入口点进单张付款单时，页面右侧悬浮面板偶尔没有出现，用户就找不到“开始采集/自动审核”的入口。
- 根因：悬浮面板由详情页 `content.js` 创建；一旦详情页脚本在 SPA 路由切换、按钮区延迟渲染或注入时机里漏掉，任何只挂在面板 root 里的按钮都会一起消失。
- 调整：把“自动审核”入口交给全站常驻的 `list_page.js` 兜底挂载：优先插到详情页 `通过 / 保存 / 转办 / 退回` 按钮右侧，找不到按钮区时显示固定小入口；点击后再补注入详情面板并派发打开事件。
- 经验：详情页关键入口要分成“页面内触发器”和“悬浮结果面板”两层。触发器应由更稳定的常驻脚本负责，面板只负责展示和执行，这样即使面板没先出现，用户也还有一个能把它拉起来的入口。

## 2026-04-16 详情页进入时只能被动读缓存，不能自动开跑审核

- 现象：用户只是点进单张付款单查看，插件却立即开始审核；如果批量缓存没被 URL 流程号命中，还会表现成“没读到缓存，进来又跑了一遍”。
- 根因：详情页初始加载和 SPA 路由切换仍传了 `autoRun=true`，缓存读取又只按 URL 里的 `processCode` 查；当 URL 只有实例 ID 时，缓存 miss 后自动审核逻辑就接管了。
- 调整：详情页进入和 route-change 一律只做被动缓存回放，不自动分析；缓存回放允许用页面快照里的付款流程号兜底查 `chrome.storage.local`，并在字段尚未稳定时做短重试。只有用户点击页面内“自动审核”按钮或面板里的开始按钮时，才允许缓存 miss 后开跑审核。
- 经验：缓存回放和自动审核是两种不同意图。页面进入最多只能做“展示已有结果”，不能把“找不到缓存”解释成“用户允许新跑一次”，否则会破坏付款单查看和审核动作之间的边界。
