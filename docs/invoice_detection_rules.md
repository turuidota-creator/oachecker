# 发票识别规则

这份文档说明“一个附件为什么会被当作发票来源”，以及“发票来源如何影响最终展示”。

## 1. 设计目标

发票识别要解决两个问题：

1. 不再只靠文件名识别发票
2. 一旦确认某个附件是发票，它在金额和公司展示上要优先于合同

典型场景：

- 文件名只是 `vsg_output_1770341207987.jpg`
- 肉眼看是一张电子发票截图
- OCR 文本里其实已经有完整发票特征

这类附件必须能被提升为发票来源。

## 2. 识别输入

每个附件在识别时可用的输入包括：

- 文件名
- URL
- 文本提取结果
- OCR 结果
- 文件类型

## 3. 强特征

命中任意一组强特征，就可以直接判为发票或高置信发票。

### 3.1 单条强特征

- `电子发票`
- `增值税专用发票`
- `增值税普通发票`

### 3.2 组合强特征

同时出现以下任意组合，也可直接高置信判为发票：

- `发票号码` + `开票日期`
- `价税合计` + `小写`
- `购买方信息` + `销售方信息`
- `税率` + `税额`
- `统一社会信用代码` + `发票号码`

## 4. 中等特征

这些词单独出现不一定能直接判成发票，但可以累计加分：

- 发票代码
- 发票号码
- 开票日期
- 购买方
- 销售方
- 价税合计
- 税额
- 税率
- 项目名称
- 规格型号
- 单位
- 数量
- 单价
- 金额
- 机器编号
- 校验码
- 电子发票服务平台

## 5. 文件名加分

文件名或 URL 命中这些词时，增加发票倾向：

- 发票
- 电子发票
- 专票
- 普票
- invoice
- 票据
- 开票

## 6. 负特征

这些词会降低“发票”的概率：

- 合同
- 协议
- 补充协议
- 开户许可
- 开户信息
- 银行账户
- 验收单
- 结算单
- 请款单
- 付款申请
- 营业执照
- 身份证

如果负特征明显，且没有足够强的发票信号，就不要误判成发票。

## 7. 当前评分思路

### 强特征

- 每命中一组：`+100`

### 中等特征

- 每命中一个：`+15`

### 文件名加分

- 每命中一个：`+20`

### 负特征

- 每命中一个：`-30`

## 8. 当前角色判定建议

- `>= 100`：直接视为 `invoice`
- `>= 60`：高置信 `invoice`
- `30 ~ 59`：`possible_invoice`
- `< 30`：`other`

当前实现里，发票来源会进入高优先队列；疑似发票会在预扫描阶段提前，但不会直接替代明确发票。

## 9. 展示优先级规则

一旦附件被识别为发票：

- 金额优先显示发票来源
- 收款公司优先显示发票来源
- 收款账号只有在发票文本里确实出现时才由发票承担

如果发票缺少账号：

- 再看银行/开户/变更附件
- 再看合同
- 再看其他附件

## 10. 与扫描顺序的关系

当前扫描顺序不是完全随机的，而是：

1. 先按业务角色
2. 同角色内，小文件优先
3. 可能是发票的小图、小 PDF、小 OFD 会提前

这样做的原因是：

- 发票常常是一张图
- 或者是一页 PDF
- 比合同大文件更容易提前给出正向命中

## 11. 样例说明

样例附件：

- `vsg_output_1770341207987.jpg`

它的文件名看不出是发票，但 OCR 文本里能命中：

- `电子发票`
- `增值税专用发票`
- `发票号码`
- `开票日期`
- `购买方信息`
- `销售方信息`
- `价税合计`
- `（小写）¥10560.78`

所以它应被判成：

- `invoice`

并且：

- 金额来源优先显示这个 JPG
- 收款公司来源优先显示这个 JPG

## 12. 当前实现建议

推荐维持三段式实现：

1. `scoreInvoiceByFilename(name, url)`
2. `scoreInvoiceByText(text)`
3. `detectInvoiceRole(item, text)`

最终输出结构建议保持：

```ts
{
  role: "invoice" | "possible_invoice" | "other",
  score: number,
  reasons: string[]
}
```

这样 hover 或调试信息里也能展示：

- 为什么被识别成发票
- 命中了哪些关键特征

## 13. 发票类型与主核对联动

从 2026-04-14 起，金额主核对不再只看“是否命中相同金额”，还会叠加发票类型口径：

- 票面细分类：统一归一成 `增值税专用发票`、`增值税普通发票`、`其他/未识别`
- 页面粗分类：统一归一成 `增值税发票`、`其他票据`、`暂未取得发票`、`未识别`

### 13.1 当前页面字段取值规则

- 优先取付款页当前显示值
- 不再把整组选项串直接当作字段值
- 对重复标签 `发票类型`，按内容再拆成：
  - 命中 `增值税发票 / 其他票据 / 暂未取得发票` 的，视为页面粗分类
  - 命中 `增值税专用发票 / 增值税普通发票 / 专票 / 普票` 的，视为票面细分类候选

### 13.2 票面类型来源优先级

1. 优先使用“命中金额的那张发票”的 OCR / 正文
2. 其次使用付款页结构化发票明细里的发票类型字段（如果 `fpSubform` 已提供）
3. 最后才看付款页可见字段里的细分类候选

### 13.3 金额卡变绿规则

只有同时满足以下条件，`金额一致` 才显示绿色：

- 已命中相同金额
- 票面识别为 `增值税专用发票`
- 页面显示为 `增值税发票`

其余情况统一显示黄色，并提示：

- `请确认发票类型`

例如：

- `专票 + 页面增值税发票` -> 金额卡绿色
- `普票 + 页面增值税发票` -> 金额卡黄色
- `专票 + 页面其他票据 / 暂未取得发票 / 未识别` -> 金额卡黄色
