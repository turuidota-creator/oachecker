# OA 系统解读指导

这份文档不是产品方案，而是面向当前项目的一份“OA 系统工作手册”。

它回答的是这几类问题：

- OA 付款单页到底有哪些数据层。
- 插件当前是怎么从页面、接口、附件里拿数据的。
- 为什么有些关联单据在 OA 页面里“明明存在”，插件却会显示未找到。
- 遇到一张异常付款单时，应该按什么顺序排查。

这份文档基于以下材料整理：

- 当前仓库里的扩展实现。
- 两次真实回放结果。
- OA 页面实际网络行为。
- 已有经验文档，如 `pitfalls_and_lessons.md` 和 `purchase_payment_related_documents_plan.md`。

## 1. 当前项目眼里的 OA 是什么

对这个项目来说，OA 不是一个单页面应用那么简单，而是 4 层叠在一起的系统：

1. 页面展示层
   - 浏览器里真正能看到的付款单页面。
   - 含表格字段、附件锚点、流程页签、审批意见等 DOM。

2. 流程详情接口层
   - 主要是 `cyouNeiOaServer/flowable/process/detail`
   - 历史流程是 `cyouNeiOaServer/history/flow/detail`
   - 这层通常比 DOM 更稳定，也更适合结构化提取。

3. 流程解析辅助接口层
   - 最关键的是 `cyouNeiOaServer/flowable/instance/instanceIdByProcessCode`
   - 它的作用是把 `GNPR-...`、`CYNCDD-...` 这类流程编码，解析成真正可访问的 `instanceId`。

4. 附件与外部文件层
   - OA 内网文件服务，如 `10.1.41.11:8081/group1/...`
   - 发票图片外链。
   - 页面展示的附件名，不等于最终可下载的真实附件 URL。

这四层里，当前插件已经稳定利用了第 1、2、4 层，对第 3 层只观察到了，还没有正式接入。

## 2. 当前插件是怎么读 OA 的

### 2.1 页面快照层

入口文件：

- `oa_finance_audit_rebuild_extension/page/collector.js`

当前做的事：

- 扫页面 DOM，提取字段对。
- 扫页面里的附件链接。
- 扫页面里的流程详情链接。
- 推出当前付款单的 `paymentTarget`：
  - `processCode`
  - `paymentAmount`
  - `payeeCompany`
  - `payeeAccount`
  - `payeeBank`
  - `paymentDate`

这层的优点：

- 不依赖接口格式。
- 能反映“用户眼前真的看到了什么”。

这层的缺点：

- 页面字段容易随样式和组件变化。
- 有些关联流程不会以完整链接形式直接出现在 DOM 里。

### 2.2 流程详情适配层

入口文件：

- `oa_finance_audit_rebuild_extension/bg/detail.js`
- `oa_finance_audit_rebuild_extension/bg/io.js`

当前做的事：

- 兼容 `flowable` 详情页。
- 兼容 `history` 详情页。
- 兼容部分旧式 `requestid` 路径。
- 从详情 payload 里补找附件和流程引用。

特别说明：

- `fetchJson` 并不是普通裸 `fetch`。
- 在有当前页 `tabId` 时，插件会把请求注入到页面主世界执行，并带上 `Authorization` / `oauthtoken` / cookie。
- 这也是为什么“在 Playwright 页里直接 fetch 可能 401，但插件里能读出来”。

### 2.3 主分析层

入口文件：

- `oa_finance_audit_rebuild_extension/bg/analyzer.js`

当前做的事：

- 合并页面快照和详情接口事实。
- 运行三项主核对：
  - 金额
  - 收款公司
  - 收款账号
- 生成关联单据区块：
  - 国内 PR
  - 采购订单
  - 验收单
  - 合同

补充：

- 当前合同摘要已经改成纯本地规则链路
- 合同摘要只走本地规则接口，不向外部服务发送合同候选条款

当前的产品口径已经固定为：

- 国内 PR：只展示，不判断。
- 采购订单：只做两条有限自动核对。
- 验收单：只展示邮件和线索，保留人工判断。
- 合同：只展示，不自动判断。

### 2.4 附件解析层

入口文件：

- `oa_finance_audit_rebuild_extension/bg/extract.js`

当前支持：

- PDF
- DOCX
- XLSX / CSV
- OFD
- 图片 OCR
- `.eml`
- `.msg`
- ZIP

当前策略：

- 能抽文本时优先抽文本。
- 扫描版 PDF 和图片用本地 OCR。
- 发票优先于其他来源。

## 3. OA 里和当前项目最相关的接口

### 3.1 付款单 / 流程详情

- `GET /cyouNeiOaServer/flowable/process/detail?procInsId={instanceId}`
- `GET /cyouNeiOaServer/history/flow/detail?requestId={requestId}&source=monitor`

作用：

- 取流程详情。
- 取 `flowFormData`。
- 取发票子表。
- 取部分子表关联关系。
- 取详情里的附件线索。

### 3.2 发票明细图

- `GET /cyouNeiOaServer/flowable/process/detailInvoiceUrl?invoiceId={invoiceId}`

作用：

- 从付款页发票子表拿到真实发票图片地址。
- 这条链路目前已经稳定工作。

### 3.3 流程编码转 instanceId

- `GET /cyouNeiOaServer/flowable/instance/instanceIdByProcessCode?processCode={code}`

作用：

- 把 `GNPR-...`
- `CYNCDD-...`
- `CYNCFK-...`
- 以及类似流程编码

解析成：

- `instanceId`
- `fromHistory`
- `title`

这条接口非常关键，因为 OA 页面经常只有“流程编码”或它的内部调用，而不直接给最终详情链接。

当前状态：

- 我们已经通过真实回放确认 OA 页面会实际调用这条接口。
- 但插件当前没有把这条数据源正式纳入关联单据提取链路。

### 4.2 回放二：`DDFK-202603060005`

结果摘要：

- 金额一致：`pass`
- 收款公司名称一致：`pass`
- 收款账号一致：`warn`

但它也暴露了两个具体缺口：

2. 合同附件分类太窄
   - 这张单里有 `2024-T-0156 保利国际广场写字楼租赁畅游.pdf`
   - 它明显很像合同类附件。
   - 但当前合同附件分类只认：
     - `合同`
     - `框架协议`
     - `采购合同`
     - `补充协议`
   - 没把“租赁”类合同识别进去。

## 5. 为什么会出现“OA 明明有，插件却没抓到”

这个问题目前已经能拆成 5 类原因。

### 5.1 页面没有直接给出最终流程链接

这类情况下，DOM 里看不到：

- `/workflow/process/detail/{id}`

但 OA 页面自身会在后台请求：

- `instanceIdByProcessCode`

也就是说：

- 用户看到的是“流程编码”。
- OA 内部再把它换成真正的 `instanceId`。
- 当前插件只认最后那条详情链接，不认中间的编码解析链。

这就是第一张单“全未找到”的主因。

### 5.2 详情子表不是所有单都稳定落在固定表里

当前 `detail.js` 已经按这些子表去抓：

- `formtable_main_154_dt1`
- `formtable_main_154_dt4`
- `formtable_main_154_dt5`
- `formtable_main_154_dt6`

但真实情况是：

- 有些单会在子表里有完整 link。
- 有些单只有编码。
- 有些单的信息埋在审批意见正文或其他字段里。

所以：

- 只扫固定子表并不够。
- 只扫 DOM 锚点也不够。

### 5.3 页面字段抽取仍然偏脆

当前字段抽取主要依赖：

- 表格两列一组的 label/value
- 若干常见表单选择器

这对付款单页够用，但对采购订单、PR、验收页不一定够稳。

表现就是：

- 能打开详情页。
- 但抽不到关键字段。
- 于是状态退化成 `warn`。

### 5.4 合同识别过度依赖关键词

当前附件分类是关键词驱动的。

优点：

- 轻量
- 易控

缺点：

- “租赁合同”“租约”“物业租赁”“房屋租赁协议”这类文件会被漏掉。
- 漏掉后就进不了合同链路，后面的合同读取和账号补证据也就跟着失效。

### 5.5 验收页不等于验收邮件

现在验收单逻辑已经能打开验收页，但“打开页”不等于“提取到了邮件线索”。

真正决定是否能给出有效验收线索的是：

- 是否有 `.eml` / `.msg`
- 是否有邮件主题字段
- 是否有正文摘要字段
- 是否有邮件附件名称

如果这些都没有，当前正确表现就是：

- `人工判断`
- 但提示“暂未提取到明确邮件线索”

## 6. 真实排查时应该怎么读 OA

建议按这个顺序看，不要一上来就盯控制台红字。

### 6.1 先看插件侧边栏

重点看：

- 三项主核对哪一项不是 `pass`
- 关联单据区是哪一块 `未找到`
- 合同参考信息有没有来源

### 6.2 再看 `result.json`

重点看这些字段：

- `analysis.paymentTarget`
- `analysis.pageSummary`
- `analysis.relatedDocuments`
- `analysis.evidencePool`
- `analysis.debug.snapshot`

特别说明：

- `analysis.debug.snapshot` 现在保存的是 `enrichedSnapshot`
- 也就是“页面快照 + 详情接口补全后的结果”
- 它比原始 DOM 快照更接近插件真实决策输入

### 6.3 再看页面网络而不是控制台噪音

优先关注：

- `flowable/process/detail`
- `history/flow/detail`
- `flowable/process/detailInvoiceUrl`
- `flowable/instance/instanceIdByProcessCode`

对当前项目来说，真正有价值的不是：

- `finance.cyou-inc.com` 的 CORS 错
- `setValue` 报错
- 各种 micro-app 红字

这些大多是 OA 页面自身噪音。

### 6.4 最后再回到源码判断“漏在哪一层”

判断方法：

- 页面里根本没有关联 link：优先看是否存在流程编码和 `instanceIdByProcessCode`
- link 有了但卡片仍然未找到：看 `parseProcessRef`
- 详情打开了但字段为空：看页面字段抽取
- 合同附件明明在但合同未找到：看附件角色分类
- 验收页打开了但没有线索：看邮件附件和正文字段

## 7. 当前对 OA 的理解边界

目前我们已经比较确定的事实：

- 付款单页不是唯一数据源。
- 详情接口比 DOM 更稳定。
- 流程编码转 `instanceId` 是实际存在且高价值的数据源。
- 页面控制台里出现的日志，不代表插件已经用了那份数据。
- 合同、PR、采购订单、验收单的“稳定可读程度”并不一样。

目前还没有完全打透的地方：

- `instanceIdByProcessCode` 的完整触发条件和覆盖范围。
- 哪些业务场景会只给编码、不给最终 link。
- 合同附件命名的更全词表。
- 采购订单页在不同模板下的字段标签差异。

## 8. 对当前工程最有价值的下一步

如果目标是把 OA 关联单据链路真正做稳，优先顺序建议是：

1. 接入 `processCode -> instanceId -> detailUrl`
   - 这是解决“页面明明有，插件却未找到”的最高收益项。

2. 补强采购订单字段抽取
   - 至少把 `supplierName` 和 `orderAmount` 抽稳。

3. 扩展合同类附件识别词表
   - 把“租赁”“租约”“物业租赁”等词加入合同分类。

4. 保持验收页逻辑轻量
   - 继续走“线索展示 + 人工判断”，不要过早做重语义引擎。

5. 继续做真实回放
   - 比读源码更快暴露“模板差异”和“数据源差异”。

## 9. 一句话总结

当前项目对 OA 的认识已经从“读付款单页面”升级成了“读付款单 + 详情接口 + 流程编码解析 + 附件文件层”。

现在真正卡住准确率的，不是 OCR，也不是三项主核对，而是：

- 关联流程解析链还没吃到 `instanceIdByProcessCode`
- 二级单据页字段抽取还不够稳
- 合同类附件分类词表还不够全

这也是后续继续扒 OA 时，最值得投入的三个点。

## 10. 2026-04-09 补充记录

### 10.1 手动打不开 OA，很多时候先看代理，不要先怀疑账号

本机后续又确认过一次真实环境：

- `WinHTTP` 是直连
- 但系统浏览器代理仍然开着，指向 `127.0.0.1:1080`

这会造成一个很容易误判的现象：

- 自动化回放脚本能进 OA
- 手动打开 Edge 却不一定能进

原因不是脚本“权限更高”，而是回放脚本启动 Edge 时显式加了：

- `--no-proxy-server`
- `--proxy-server=direct://`
- `--proxy-bypass-list=*`

因此当前仓库里已经补了两类代理排障脚本：

- `scripts/open_oa_direct.ps1`
- `scripts/open_oa_direct.cmd`
- `scripts/set_oa_proxy_bypass.ps1`

它们分别用于：

- 用直连模式启动 Edge 打开 OA
- 给系统浏览器代理补 `oa.cyou-inc.com` / `*.cyou-inc.com` / `10.*` 等例外名单

对当前项目来说，这条经验很重要：

- “我这里能进，你那里不能进”优先排查代理
- 不要先怀疑账号、cookie 或插件逻辑

### 10.2 侧边栏“有内容但看不到、也滚不下去”通常是容器高度关系错了

这轮真实页面里出现过一个典型 UI 症状：

- 关联单据和合同摘要都已经渲染出来了
- 但面板下半部分被截断
- 鼠标滚轮也没法往下滚

最终定位不是数据问题，而是布局问题：

- 外层 `#oa-finance-rebuild-root` 只有 `max-height`
- 内层卡片没有真正被限制在固定高度内
- 结果 `.oa-finance-rebuild-card` 实际高度长到了视口外面
- `.oa-finance-rebuild-body` 又因为没得到明确剩余高度，`scrollHeight` 和 `clientHeight` 相等
- 所以浏览器判定“内部不需要滚动”

当前修法已经固定为：

- 外层容器使用 `top + bottom` 确定高度
- 卡片使用 `height: 100%`
- 真正可滚动的区域只保留在 `.oa-finance-rebuild-body`

这类问题的排查方法也可以固化：

1. 先看 `result.json` 里的 `panel_state.bodyText`，确认内容是不是已经在 DOM 里
2. 再测 `.oa-finance-rebuild-body` 的 `clientHeight / scrollHeight / scrollTop`
3. 如果内容在、但 `canScroll = false`，优先看容器高度关系，不要先怀疑数据采集

### 10.3 补充协议不写付款条款，不等于“合同信息没提出来”

真实案例：`DDFK-202602040012`

这张单的合同链路其实已经跑通：

- 命中了合同流程页
- 读到了合同页附件
- 抽到了补充协议、报价单、合同变更协议等文本

但旧逻辑仍然会显示：

- “已进入合同页，但未提取到明确付款条件”
- 多个字段是“未明确”

根因不是没读到合同，而是这类合同的结构和普通采购合同不一样：

- 合同主体是“补充协议”
- 正文重点是“新增服务内容”和“原合同继续有效”
- 付款条件并不总是直接写成“付款方式 / 付款条件 / 支付条款”
- 费用细节往往散落在报价单或附件费用表里

例如这张单里，真正有用的信息更像是：

- `2.2 本协议未尽事宜，按原合同约定执行`
- `SD-WAN服务（重庆） 10M ¥2,800`
- `月租服务费用`

所以当前项目对合同摘要的理解又往前走了一步：

- “没有直接命中付款关键词”不代表没有可展示合同信息
- 对“补充协议 + 报价单 / 费用表”组合，要允许做回退摘要
- 回退摘要优先展示：
  - 是否明确写了“按原合同约定执行”
  - 是否能提到月租 / 月费 / 一次性费用 / 报价金额
  - 是否能提到服务期 / 自动续期

也就是说，当前合同摘要已经不再只靠“付款 / 支付 / 结算”几个字触发。

### 10.4 当前合同摘要的实际策略已经变成“两层”

对合同来说，现在更准确的描述不是“有摘要 / 没摘要”，而是两层：

1. 显式条款层
   - 直接从合同页表单或合同正文里抽“付款条件”“验收条件”“发票条件”等

2. 补充协议回退层
   - 当显式条款抽不到时
   - 尝试从补充协议、报价单、费用表中提炼：
     - 原合同继续有效
     - 月租 / 月费 / 一次性费用
     - 服务期 / 自动延期

这层策略的价值在于：

- 它不会假装已经拿到了完整付款条款
- 但也不再把“补充协议类合同”误判成“什么都没提出来”
